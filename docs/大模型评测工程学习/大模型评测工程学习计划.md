## 与 AI-Agent学习计划.md 的关系

那份计划的目标是"会**做** Agent"(Agent 开发岗视角),本计划的目标是"会**评测** Agent"(评测工程岗视角)。

**本计划为求职主线**,原因:
1. 目标岗位 JD 明确要求"扎实的软件测试与质量保证基础"——这是现有 5 年经验的直接变现,而 Agent 开发岗要和科班/大厂开发者正面竞争。
2. 评测是新兴细分岗(形成约 1–2 年),没有"十年老兵"压制,缺的正是"懂测试方法论 + 能写工程代码"的组合。
3. Agent 概念仍要学,但只学"评测视角"(能解剖,不必能生产)。原计划的阶段 1/2 中与工具调用、错误处理相关的内容已收编进本计划阶段 2 的玩具 Agent;阶段 3(RAG)、阶段 4(框架/MCP)、阶段 5(多 Agent)在本主线中降级为【了解】,不投入开发时间。

## 三、阶段 1:评测方法论(9.7 – 9.20,约 22h)

### 学习目标
建立评测岗的**语言体系**并跑通第一个完整评测闭环:评测集 → 执行 → 打分 → 结论。

### 1a. 概念体系(9.7 – 9.11,平日 5 天,每天 1 主题)

每天读资料 + 用自己的话写 200 字笔记存入 `llm-eval-lab/docs/`(强制输出,防"读了就忘")。

| 天 | 主题 | 知识点与程度 |
|---|---|---|
| D1 | 评测维度划分 | 准确性/相关性/忠实度(幻觉)/指令遵循/安全性/拒答能力【必须】;各维度适用任务【必须】 |
| D2 | 客观指标 | Exact Match、F1、pass rate、pass@k 的计算方式与适用场景【必须】;BLEU/ROUGE【了解】 |
| D3 | 评测集构建 | 覆盖度、难度分层、金标准来源、边界/难例设计【必须】;评测集版本管理【建议】 |
| D4 | LLM-as-Judge | 原理(G-Eval/MT-Bench 范式)【必须】;位置偏差、长度偏差、自我偏好、增强偏差【必须,面试必问】;缓解手段(交换顺序、CoT 打分、多数投票)【必须】 |
| D5 | 评测体系陷阱 | 数据污染【必须,概念】、benchmark 饱和(MMLU)【了解】、静态榜单弊端【了解】;人工对齐(与人工标注的一致率)【必须】 |

**为什么**:评测岗面试 60% 是概念判断题("你会怎么设计 XX 的评测维度"),答不上不是因为不会做,是没建立术语映射。这一周就是建立映射。

**补漏**:D5 顺带写一页 RAG 评测概念笔记(检索命中率 / 忠实度 / 答案相关性)【了解】--RAG 评测是评测岗 JD 高频词,概念能聊两句即可,不投入开发;试水反馈确有需要再升级为实操。

### 1b. DeepEval 上手(9.12 – 9.16,5 天,含一个周末)

| 自定义 metric(自定义评分标准) | 【必须,面试能讲"我自定义过指标"】 |

### 1c. 第一份评测报告(9.17 – 9.20,4 天)

**做什么**:
0. 前置(9.16 前完成):注册第二家厂商并充值最小额度(现有火山方舟 glm 接入,则补 DeepSeek 开放平台)——注册审核与到账时间不吃主线

## 四、阶段 2:作品集项目(9.21 – 11.1,约 60h)★ 全计划核心

### 学习目标
产出一个命中评测岗 JD 全部关键词的完整作品集:**车载日志分析 Agent 的评测流水线**。

### 选题(9.21 定死,之后不再改)
**被测对象**:先用 1–2 晚写一个约 100 行的玩具 Agent(LLM + 2–3 个工具:解析日志时间戳 / 按级别过滤 / 统计错误),**评测它**。

**为什么这个选题**:
1. 蹭车载域经验:评测集素材来自你见过的真实日志场景,面试官看到的是"领域判断"而非"照抄教程"
2. 命中 JD 原词:Agent 全链路评测、工具调用评测、轨迹、多轮、评测集构建、badcase 归因闭环
3. 域素材无限,不会中途"没东西可测"

**比例铁律:写 Agent 占 10% 时间,评测它占 90%。** 你是评测工程师,不是 Agent 开发工程师。

### Week 1(9.21 – 9.27):评测集设计

| 知识点 | 程度 |
|---|---|
| Agent 评测四层维度:意图理解 → 工具选择正确性 → 参数准确性 → 最终结果质量 | 【必须,对应腾讯 JD 原文】 |
| 轨迹(trace)评测 vs 结果评测 | 【必须】 |
| 每条用例的金标准:预期调用哪个工具、什么参数、什么结果 | 【必须】 |
| 难例设计:模糊指令、多工具组合、应拒绝的场景、参数幻觉诱饵 | 【必须】 |
| 玩具 Agent 的 Function Calling 流程(定义→决策→执行→回填) | 【必须,写玩具时顺带掌握】 |
| Agent 终止条件与死循环防护 | 【了解,被测对象视角】 |

**任务**:手写 50–100 条任务,每条带金标准;其中 ≥10 条为多轮任务(追问 / 修正口径 / 上下文依赖),对应 JD"多轮"关键词。
**为什么**:评测集是评测工程师的核心产出物,面试必问"你的评测集怎么设计的"。用例设计是你 5 年测试的看家本领,这周做满,是你赢过科班应届生的部分。

### Week 2(9.28 – 10.11,含国庆):自动化流水线

| 知识点 | 程度 |
|---|---|
| 批量执行 → 分层打分 → 聚合 → 生成 markdown 报告 | 【必须】 |
| 全部用 pytest 组织(参数化 + fixture) | 【必须】 |
| GitHub Actions 跑流水线 | 【必须】 |
| 结果落 JSON + 自动 diff 回归("哪些 case 退化了") | 【必须,点睛之笔】 |
| 失败用例截图/trace 落盘,便于归因 | 【建议】 |
| 成本核算:每次全量评测的 token 费用(复用 LLMClient 的成本统计) | 【必须,车载质量思维+LLM 特有维度】 |

**任务**:流水线全绿后,仓库推送 GitHub 公开远程并挂 Actions 徽章(阶段 3 的简历需要可点开的项目链接,本地 git init 不覆盖这一步)。
**为什么**:"自动化评测流水线 + 回归"是 JD 原词;回归 diff 把车载"版本迭代防静默回归"思维原样迁移--这正是 JD 里"非确定性输出的回归评测方案"要的东西。
**注意**:国庆假期是最大风险窗口,提前设定假期最低投入(每天 1h 只跑不学新),保证连击不断。

### Week 3(10.12 – 10.18):Judge 深度

| 知识点 | 程度 |
|---|---|
| judge prompt 设计(评分标准、输出格式) | 【必须】 |
| 偏差实验:交换候选顺序、长短答案对比、judge 模型自评 vs 互评 | 【必须,面试深水区】 |
| judge 与人工一致率计算(抽检 20 条;口径分原始一致率与 Cohen's Kappa,后者排除随机一致) | 【必须】 |
| "何时可信 judge / 何时必须人工"的决策结论 | 【必须】 |

**为什么**:LLM-as-Judge 是面试必问的深度题,也是拉开"只会调库的人"差距的地方。报得出一致率数字的人和只说"我用了 G-Eval"的人是两个档次。

### Week 4(10.19 – 10.25):badcase 归因闭环

| 知识点 | 程度 |
|---|---|
| 失败 case 分类归因:模型能力 / prompt 设计 / 工具实现 bug / 评测集本身有错 | 【必须】 |
| 各修一批 → 回归验证 → 写"修复前后对比" | 【必须】 |
| 评测集自身的迭代(发现金标准错) | 【必须,体现严谨性】 |

**为什么**:"badcase 分析与治理闭环"是 JD 最高频词。归因四分类直接映射你 XSAN 专项的问题定位经验,这周内容就是面试"讲一个你解决过的复杂问题"的弹药。

### Week 5(10.26 – 11.1):打磨发布

**任务**:README 重写(5 分钟看懂"测什么/怎么测/结论是什么")、修所有 TODO、清理 debug 代码、补 2 个核心单测。
**为什么**:面试官平均只花 5–10 分钟看 repo,项目再深,讲不明白 = 0 分。这周只做表达,不加功能。

## 六、阶段 4:试水面试(12.1 – 1.31,约 20h + 面试时间)

### 学习目标
用真实市场反馈校准,不追求 offer,追求情报。

### 具体任务
1. 投 5–10 家中小厂/AI 应用公司的评测/测试开发岗
2. 每次面试后记录:被问倒的问题、JD 里自己没有的词(预计常见缺口:RAG 评测、多模态、评测平台经验)
3. 每月把反馈回灌项目:缺什么补什么,只补 2–3 周,不盲目大补
4. 维护个人面试题库(见下)

### 为什么
真实市场反馈 > 任何自我评估。试水期拿到"你缺 RAG 评测经验"的信号,能让你主投前精准补 2–3 周,而不是盲目再学三个月。

### 面试高频题清单(评测岗版,持续补充)
1. 你的评测集怎么设计的?覆盖度怎么保证?
2. LLM-as-Judge 有哪些偏差?你怎么缓解、怎么验证?
3. 客观指标和主观评测分别适用什么场景?
4. 模型版本更新后怎么做回归评测?非确定性输出怎么设计准出标准?
5. badcase 归因怎么做?怎么区分模型问题还是链路问题?
6. Agent 评测和普通 chatbot 评测的区别?
7. 数据污染是什么?怎么判断你的评测集被污染了?
8. Judge 和人工不一致的 case 怎么处理?
9. 你的评测流水线本身怎么保证不引入回归?
10. (车载相关)传统测试和 LLM 评测最大的方法论差异是什么?(答案锚点:非确定性输出、无穷输入空间、准出从"对错"变"分布")

## 八、每日节奏模板(工作日 1.5–2h)

1. **10 分钟**:看昨天的 commit/笔记,回忆卡在哪
2. **70–90 分钟**:只做一个动作——写代码 / 跑实验 / 修 badcase,文档只查当下用到的
3. **10 分钟**:commit + 一行日志(今日做了什么、卡在哪、明天做什么)

时间配比(贯穿全程):**80% 写代码,20% 查资料。**"先看完两门课再动手"是过去一年的复发信号,出现即警觉。

daily log 会自动积累成 12 月的空窗叙事素材。

## 九、护栏(贯穿全程)

1. **选题 9.21 定死后不再换**。中途冒出的"更好的选题"是拖延症的马甲。

3. **一切代码在个人电脑 + 个人网络完成**,不碰公司账号/仓库/Wi-Fi;repo 从第一天按可公开标准管理。
4. **阶段出口不达标就顺延,不跳阶段**。
5. **国庆 / 春节等长假设最低投入**(每天 1h 只跑不学新),防连击断裂。
6. AI 当导师:概念看不懂就换方式解释,写完代码让它 review——但 review 结论要自己判断,不盲从。
