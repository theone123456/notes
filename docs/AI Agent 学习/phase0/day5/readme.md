# Day 5 学习笔记：核心参数实验

> 核心命题：采样参数是模型生成文本的"控制旋钮"--它不改变模型知道什么，只改变模型如何从候选中选择
> 产出脚本：`temperature_experiment.py`、`max_tokens_experiment.py`

## temperature：控制输出的随机性

> 来源：API 文档的采样参数 · 目的：理解模型如何在每一步从多个候选 token 中"做选择"，以及如何用 temperature 控制这个选择的确定程度

LLM 生成文本时，并非直接输出一个词。它在每个位置做的是：给词表中所有 token 各打一个原始分数（logit），然后从中选一个。**temperature 就是插在"打分"和"选择"之间的一个缩放器**，控制概率分布的"陡峭程度"。

**取值范围**：通常为 **0 ~ 2.0**（OpenAI 等主流 API 的标准范围）。T=0 走 argmax 特判，T=1 使用模型原始分布，T>1 增强随机性。不同服务商的上限可能略有差异。

### 生成流水线：logits -> temperature -> softmax -> 采样

```text
输入上下文
  ↓
Transformer 前向传播
  ↓
logits（词表大小 N 的原始分数向量）     ← 每个候选 token 一个分数，未归一化
  ↓
temperature 缩放：logit_i / T            ← temperature 在这里介入
  ↓
softmax（转为概率分布，和为 1）
  ↓
采样（按概率随机选一个 token）
  ↓
追加到序列，回到第一步，重复
```

**关键**：temperature 作用在 **logits 上**（softmax 之前），不是作用在已经算好的概率上。它改变的是概率分布的**形状**，不是模型的"知识"。

### 数学公式

```text
标准 softmax（T=1）：       P(token_i) = exp(z_i) / Σ exp(z_j)

带 temperature 的 softmax： P(token_i) = exp(z_i / T) / Σ exp(z_j / T)

其中 z_i 是 token_i 的 logit，T 是 temperature
exp(x) 是 e 的 x 次幂（e ≈ 2.718，自然常数）
注意：exp 对任何有限输入都返回正数，所以 logit=0 时 exp(0)=1，概率不为 0
      只有 logit=-∞ 时 exp(-∞)=0，概率才真正为 0
```

T 在分母里：除以 T 就是缩放 logits 之间的**差距**：

| T 值 | 操作 | logits 差距 | 分布形状 | 效果 |
|---|---|---|---|---|
| T -> 0 | 除以极小数，差距被放大 | 极大 | 尖峰 | 概率几乎全集中在一个 token 上（逼近 argmax） |
| T = 1 | 除以 1，不变 | 原样 | 模型原始分布 | 模型训练时学到的自然分布 |
| T > 1 | 除以较大数，差距被缩小 | 变小 | 平坦 | 概率被铺平，低概率 token 也有机会被选中 |

> 一句话：T 小则分布尖锐（确定性高），T 大则分布平坦（随机性强）。

### 用具体数字感受一下

假设 5 个候选 token，logits 分别为 `[4, 3, 2, 1, 0]`，对比三个 temperature 下的概率分布：

| Token | logit | T=0.5 | T=1.0 | T=2.0 |
|---|---|---|---|---|
| A | 4 | 86.5% | 63.6% | 42.9% |
| B | 3 | 11.7% | 23.4% | 26.0% |
| C | 2 | 1.6% | 8.6% | 15.8% |
| D | 1 | 0.2% | 3.2% | 9.6% |
| E | 0 | 0.0% | 1.2% | 5.8% |

```text
T=0.5：A 独占 86.5%，几乎每次都选 A → 确定性强
T=1.0：A 占 63.6%，B 也有 23.4% → 模型的自然分布
T=2.0：A 降到 42.9%，E 从 0% 升到 5.8% → 铺平，谁都有机会
```

> 观察：T 从 0.5 升到 2.0，A 的概率从 86.5% 降到 42.9%，E 从几乎不可能变成有 5.8% 的机会。temperature 没有"增加随机性"，而是**压缩了高低概率之间的差距**。

### 为什么不直接用 greedy（永远选第一名）？

greedy decoding（贪心解码）= 每步选概率最高的 token = temperature 趋近 0 的极限。它确定性最高，但有两个问题：

| 问题 | 说明 | 例子 |
|---|---|---|
| 输出枯燥 | 同一 prompt 永远得到同一回复，聊天机器人像复读机 | 每次问"你好"都回"你好！有什么可以帮你的吗？" |
| 重复循环 | 一旦选了某个 token，上下文让模型更倾向选它，形成死循环 | "I think I think I think I think..." |

```text
为什么重复循环会发生：
1. 模型选了 "I think" 作为下一个 token
2. "I think" 进入上下文后，模型判断"接 I think"的概率最高
3. greedy 无条件选最高概率 → 又选 "I think"
4. 死循环，没有逃逸机制
```

> 采样（temperature > 0）的引入就是为了解决这两个问题：引入随机性，让模型有时选"第二名"，打破循环、增加多样性。

### temperature 的局限：长尾问题

temperature 能铺平分布，但**无法剔除**概率极低的 token。词表有几万个 token，即使每个只有 0.001% 的概率，累积起来也不可忽略。temperature 调高时，这些"荒谬 token"也会获得非零的选中机会：

```text
问："法国的首都是哪里？"
  候选概率（temperature=2.0 时）：
    "巴黎"     42%
    "伦敦"     15%
    "里昂"      8%
    ...
    "木琴"     0.3%    ← 概率很低，但不是 0，有被选中的可能

  -> 高 temperature 下，模型可能输出"法国的首都是木琴"（幻觉）

> 实验验证：glm-5.2 在 T=2.0 下未出现乱码或偏离主题（见下方实验记录），实际效果受模型实现和 prompt 类型制约，理论上的"幻觉"风险并非必然发生。
```

> 这就是 top_p（核采样）要解决的问题--Step 2 会讲。temperature 管"分布形状"，top_p 管"候选池范围"。

### temperature=0 的工程现实

```text
数学上：T=0 时 z_i / 0 无定义（除以零）
工程上：API 遇到 T=0 通常直接走 argmax（取 logit 最大的 token），跳过 softmax
```

但 **temperature=0 不等于 100% 可复现**：

| 因素 | 说明 |
|---|---|
| 浮点精度 | GPU 浮点运算的非确定性，不同批次可能有微小差异 |
| 模型版本 | 服务商可能负载均衡到不同版本的模型实例 |
| 批处理效应 | 请求被分到不同 batch，计算路径不同 |

**关键机制**：非确定性发生在**前向传播（logits 计算）阶段**，不在采样阶段。T=0 保证的是"给定相同 logits，一定选 argmax"，但不保证"两次请求算出相同 logits"：

```text
同一 prompt 两次请求，T=0：

请求 1 前向传播 -> logits = [4.0001, 3.9999, 2.0, 1.0, 0.0] -> argmax = A
请求 2 前向传播 -> logits = [3.9998, 4.0002, 2.0, 1.0, 0.0] -> argmax = B

两次都走 argmax，但 logits 的微小差异让 argmax 结果翻转
```

> 一句话：temperature=0 是"尽可能确定"的约定，不是数学上的硬保证。需要可复现时用它，但不要假设 bit 级一致。

### 实践指南：什么场景用什么值

| 场景 | 推荐 temperature | 原因 |
|---|---|---|
| 代码生成 / 数据提取 / 事实问答 / JSON 输出 | 0 ~ 0.3 | 需要确定性、准确性，不能"发挥" |
| 通用对话 / 摘要 / 翻译 | 0.3 ~ 0.7 | 平衡准确与自然 |
| 创意写作 / 头脑风暴 / 起名 | 0.7 ~ 1.2 | 需要多样性和创造力 |
| 故意制造随机 / 测试鲁棒性 | 1.5 ~ 2.0 | 探索模型在极端条件下的行为 |

**关键认知**：

1. **temperature 作用在 logits 上，不是概率上**：它在 softmax 之前缩放原始分数，改变的是分布形状，不是模型的"知识"
2. **低 temperature = 尖峰分布 = 确定性高**：概率集中在最高分 token 上，输出稳定可复现
3. **高 temperature = 平坦分布 = 随机性强**：低概率 token 获得机会，输出多样但可能偏离主题甚至产生幻觉
4. **greedy（T->0）有两个缺陷**：输出枯燥 + 重复循环，这是采样机制存在的根本原因
5. **temperature=0 不是硬保证**：非确定性发生在前向传播（logits 计算）阶段而非采样阶段，T=0 保证"给定相同 logits 选 argmax"，但不保证"两次请求算出相同 logits"

> 一句话：temperature 是概率分布的"对比度旋钮"--调低让模型更"自信"，调高让模型更"发散"，它不改变模型会什么，只改变模型怎么选。

## 本节记住五件事

1. temperature 作用在 logits 上（softmax 之前）：`P = softmax(logit / T)`，改变分布形状而非模型知识
2. T < 1 锐化分布（确定性高），T > 1 平滑分布（随机性强），T = 1 是模型自然分布
3. greedy decoding（T->0）的两大缺陷：输出枯燥 + 重复循环，这是采样存在的根本原因
4. temperature 无法剔除长尾低概率 token，这是 top_p 要解决的问题
5. 实践：代码/数据提取用 0~0.3，创意写作用 0.7~1.2，temperature=0 是"尽可能确定"的约定而非硬保证

## top_p：核采样

> 来源：API 文档的采样参数 · 目的：解决 temperature 无法剔除长尾低概率 token 的问题，控制"候选池范围"

temperature 通过缩放 logits 改变概率分布的**形状**，但无法剔除任何 token--所有 token 都保留非零概率。**top_p（核采样 / nucleus sampling）从另一个角度切入：直接砍掉概率太低的候选 token，只从"靠谱"的候选池里采样。**

### 机制：按累积概率截断候选池

```text
完整采样流水线中 top_p 的位置：

logits -> temperature 缩放 -> softmax（概率分布）-> top_p 截断 -> 重归一化 -> 采样
                                                          ↑
                                                       top_p 在这里介入
```

**top_p 的操作步骤**：

```text
1. 所有 token 按概率从高到低排序
2. 从头开始累加概率，直到累积值 >= p
3. 只保留参与累加的这些 token（"核"），其余全部丢弃
4. 对保留的 token 重新归一化（让概率和重新为 1）
5. 从这个缩小后的候选池中采样
```

> 一句话：temperature 管"分布形状"（尖还是平），top_p 管"候选池范围"（保留多少 token）。

### 用具体数字感受一下

假设 softmax 后 8 个 token 的概率分布如下：

```text
排序后：A=50%  B=20%  C=12%  D=8%  E=4%  F=3%  G=2%  H=1%
```

对比不同 top_p 值的截断效果：

| top_p | 累积过程 | 保留的 token | 丢弃的 token | 效果 |
|---|---|---|---|---|
| 0.1 | A(50%) 已 >= 10% | A | B~H | 极度保守，几乎只选第一名 |
| 0.9 | A+B+C+D = 90% | A, B, C, D | E, F, G, H | 砍掉长尾，保留合理候选 |
| 1.0 | 全部累积 = 100% | A~H | 无 | 不截断，所有 token 都有资格 |

```text
top_p=0.1 的截断：
  A=50%  累积 50% >= 10%  -> 停！只留 A
  B~H 全部丢弃
  重归一化：A=100%
  -> 等效于 greedy decoding

top_p=0.9 的截断：
  A=50%  累积 50%
  B=20%  累积 70%
  C=12%  累积 82%
  D=8%   累积 90% >= 90%  -> 停！留 A,B,C,D
  E,F,G,H 丢弃（"木琴"这类荒谬词永远不会被选中）
  重归一化：A=55.6%  B=22.2%  C=13.3%  D=8.9%
```

> 关键观察：top_p=0.9 砍掉了 E~H，但保留了 A~D 四个合理候选。它不是固定保留前 N 个（那是 top_k），而是**按概率质量动态截断**--分布集中时少保留几个，分布平缓时多保留几个。

### top_p vs temperature：形状 vs 范围

| 对比维度 | temperature | top_p |
|---|---|---|
| 操作对象 | logits（softmax 之前） | 概率（softmax 之后） |
| 操作方式 | 缩放 logits 差距，改变分布**形状** | 截断候选池，改变**范围** |
| 是否剔除 token | 否，所有 token 概率改变但都保留 | 是，低于累积阈值的 token 被直接丢弃 |
| 能否消除长尾 | 否，高 temperature 下长尾反而被放大 | 是，低概率 token 被物理剔除 |
| 取值范围 | 0 ~ 2.0 | 0 ~ 1.0 |
| 极端值效果 | T=0 逼近 greedy | top_p=0 逼近 greedy |

> 一句话：temperature 调的是"概率分布的对比度"，top_p 调的是"候选池的门槛"。

### 为什么不建议同时调整 temperature 和 top_p

OpenAI 官方建议**二选一调整**，另一个保持默认值。原因：

```text
temperature 改变分布形状 -> top_p 在改变后的分布上截断
                ↑                 ↑
            第一步               第二步（依赖第一步的结果）
```

两者串行执行，互相影响：

| 问题 | 说明 | 例子 |
|---|---|---|
| 效果不可预测 | temperature 先把分布铺平/聚拢，top_p 再在新分布上截断，最终结果难以直觉推断 | T=1.5 + top_p=0.9：铺平后截断保留的 token 集合，与 T=0.5 + top_p=0.9 完全不同 |
| 调试困难 | 改一个参数，另一个的截断效果也跟着变，无法控制变量 | 出问题时不知道是 temperature 的锅还是 top_p 的锅 |
| 可能互相抵消 | T 调高增加随机性，top_p 调低减少随机性，两者方向相反，效果抵消 | T=1.5（铺平）+ top_p=0.3（截断到只剩 1-2 个 token）≈ 确定性输出，白调了 |

**实践**：用 temperature 控制随机性时，top_p 保持默认 1.0（不截断）；用 top_p 控制候选池时，temperature 保持默认 1.0（不缩放）。绝大多数场景只调 temperature 就够了。

> 一句话：两个旋钮同时转，你不知道谁在起作用--调一个、留一个默认，才好判断效果。

### 实践指南

| 场景 | 推荐 top_p | 原因 |
|---|---|---|
| 代码生成 / 数据提取 / 事实问答 | 0.1 ~ 0.3（或用 temperature=0 替代） | 只保留最高概率候选，减少噪声 |
| 通用对话 / 摘要 | 0.9（默认） | 砍掉长尾荒谬词，保留合理候选 |
| 创意写作 / 头脑风暴 | 0.95 ~ 1.0 | 保留更多候选，增加多样性 |

**关键认知**：

1. **top_p 截断的是候选池，不是概率形状**：物理丢弃低概率 token，被丢弃的 token 永远不会被选中
2. **动态截断是核心优势**：不固定保留前 N 个，而是按概率质量累积截断，分布集中时少留、平缓时多留
3. **与 temperature 二选一**：同时调整会让效果不可预测，调试困难，可能互相抵消
4. **top_p=1.0 等于不截断**：所有 token 都保留，top_p=0 等效于 greedy decoding
5. **绝大多数场景只调 temperature 就够**：top_p 保持默认 1.0，用 temperature 控制随机性是更直觉的做法

> 一句话：top_p 是候选池的"门槛"--设低只留最靠谱的，设高放更多候选进来；和 temperature 别同时调，否则你不知道谁在起作用。

### 本节记住五件事

1. top_p（核采样）按累积概率截断候选池：排序后累加到 p 就停，保留的采样，丢弃的永不被选
2. 取值范围 0~1.0：top_p=0 逼近 greedy，top_p=1.0 不截断（所有 token 保留）
3. 与 temperature 的区别：temperature 改变分布形状（logits 层），top_p 改变候选池范围（概率层）
4. 不建议同时调整：两者串行执行互相影响，效果不可预测，可能互相抵消
5. 实践：大多数场景只调 temperature，top_p 保持默认 1.0

## max_tokens：输出上限回顾

> 来源：Day 4 已详细学习，本节为回顾确认 · 目的：将 max_tokens 与 temperature/top_p 放在同一框架下理解

Day 4 在[上下文窗口](../day4/readme.md#上下文窗口context-window)节已详细学习 max_tokens，这里做简要回顾并补充参数视角的对比。

### 核心要点回顾

```python
response = client.chat.completions.create(
    model=MODEL,
    messages=messages,
    max_tokens=1000,  # ← 限制输出不超过 1000 token
)
```

| 要点 | 说明 |
|---|---|
| 管的是输出 | 限制 `completion_tokens`（模型回复），不管输入 |
| 截断信号 | 回复撞到限制被截断时，`finish_reason` 返回 `"length"` |
| 隐含约束 | max_tokens 有**两个独立上限**，任意一个超出都会报错（见下方详解） |
| 不设会怎样 | 使用服务商默认上限，通常远小于完整窗口（如默认 4K 而非 128K）。注意：服务商默认上限 ≠ 模型最大输出限制，见下方区分 |
| 与上下文窗口的关系 | 窗口是硬上限（模型架构决定），max_tokens 是你在上限内主动设的"刹车" |

### 模型最大输出限制 vs 服务商默认上限

这两个概念容易混淆，但不是同一个东西：

| 概念 | 含义 | 作用 |
|---|---|---|
| 模型最大输出限制 | 模型单次能生成的**绝对上限**，由模型架构决定 | max_tokens 参数不能超过这个值，否则请求报错 |
| 服务商默认上限 | 不设 max_tokens 时，服务商自动使用的值 | 可能等于模型最大输出，也可能远小于它 |

```text
举例（假设值）：
  上下文窗口：       128K（输入+输出的总和上限）
  模型最大输出限制：  8K（单次最多生成 8K token，max_tokens 不能超过这个值）
  服务商默认上限：   4K（不设 max_tokens 时，只给 4K 就截断）

三种情况：
  max_tokens=2K    -> 生成到 2K 截断（finish_reason="length"）
  max_tokens=10K   -> 报错（超过模型最大输出 8K）
  不设 max_tokens   -> 生成到 4K 截断（服务商默认值，finish_reason="length"）
```

> 关键：模型最大输出是"天花板"（不能突破），服务商默认是"不设时的自动值"（可能远低于天花板）。不设 max_tokens 不等于"不限制"，而是用服务商的默认值，可能意外截断长输出。

### max_tokens 的两个独立上限

```text
上限 1：上下文窗口剩余空间
  max_tokens ≤ 上下文窗口 - 输入已占 token
  超出 -> 请求报错（请求阶段，未生成）

上限 2：模型最大输出限制
  max_tokens ≤ 模型最大输出 token 数
  超出 -> 请求报错（参数校验阶段，未生成）
```

这两个上限是**独立约束**，不是"取较大值"：

```text
场景举例（假设上下文窗口 1024K，模型最大输出 128K）：

max_tokens=256K
  上限 1：1024K - 输入(假设 10K) = 1014K >> 256K  -> 通过
  上限 2：128K < 256K  -> 超出，报错

max_tokens=64K
  上限 1：1014K >> 64K  -> 通过
  上限 2：128K > 64K  -> 通过
  -> 生效，最多生成 64K token
```

> 关键：上下文窗口管"能装多少"（输入+输出总和），模型最大输出管"能生成多少"（仅输出）。max_tokens 必须同时满足两个约束。模型最大输出通常远小于上下文窗口（如窗口 128K 但最大输出仅 4K~8K），原因见 Day 4 的 [prefill vs decode](../day4/readme.md#为什么最大输入--最大输出--最大思考) 分析。

### 三个参数的定位对比

temperature、top_p、max_tokens 是 API 请求中最核心的三个参数，但它们管的维度完全不同：

| 参数 | 管什么 | 操作阶段 | 类比 |
|---|---|---|---|
| temperature | 输出**有多随机** | 采样阶段（缩放 logits） | 调"对比度" |
| top_p | **哪些 token 有资格**被选 | 采样阶段（截断候选池） | 设"门槛" |
| max_tokens | 输出**最多多长** | 生成阶段（截断输出长度） | 踩"刹车" |

```text
一次请求的参数控制链：

输入处理（不受这三个参数影响）
  ↓
logits 计算（不受这三个参数影响）
  ↓
temperature 缩放    ← 控制随机性
  ↓
softmax
  ↓
top_p 截断          ← 控制候选池范围
  ↓
采样选 token
  ↓
逐个生成输出
  ↓
max_tokens 截断     ← 控制输出长度
```

> 关键：temperature 和 top_p 是**采样参数**（控制"怎么选"），max_tokens 是**输出控制参数**（控制"选多久停"）。前两个影响每个 token 的选择方式，第三个只管总长度。

### 本节记住四件事

1. max_tokens 管的是**输出长度**（completion_tokens），不管输入；截断时 `finish_reason="length"`
2. max_tokens 有**两个独立上限**：上下文窗口剩余空间 和 模型最大输出限制，必须同时满足
3. 不设 max_tokens 会使用服务商默认上限（通常远小于完整窗口），可能意外截断长回复
4. 三个核心参数定位不同：temperature 管"随机性"，top_p 管"候选池"，max_tokens 管"输出长度"

## 实验记录：temperature 稳定性对比

> 产出脚本：`temperature_experiment.py` · 模型：glm-5.2
> 目的：验证 temperature 高低对输出稳定性的影响，对比标准问题与创意问题的差异

### 实验设计

两组问题，各在 temperature=0/1.0/2.0 下调用 3 次，共 18 次。每次记录回复内容和 completion_tokens。

```text
标准问题（概率分布集中，模型有强先验）：
  "用一句话解释什么是人工智能"

创意问题（概率分布平缓，候选词多差距小）：
  "用一个意想不到的比喻描述人工智能，越有创意越好"
```

### 实验结果

**标准问题** -- 3 次回复内容对比：

| temperature | 输出一致性 | 内容差异 | completion_tokens |
|---|---|---|---|
| 0 | 语义近似，措辞不同 | "让机器模拟人类的感知/学习/推理和决策能力" vs "让计算机或机器模拟人类的学习、推理和解决问题的能力" vs "让机器通过算法和数据，模拟人类的感知..." | 657, 809, 931 |
| 1.0 | 语义近似，措辞不同 | 同样围绕"模拟人类智能/学习/推理"展开，细节措辞各异 | 742, 638, 808 |
| 2.0 | 语义近似，措辞不同 | 仍为标准定义，无乱码、无偏离主题 | 703, 657, 652 |

**创意问题** -- 3 次回复的比喻主题对比：

| temperature | 比喻主题 | 一致性 | completion_tokens |
|---|---|---|---|
| 0 | ① 香水蒸馏器　② 幻影泥瓦匠　③ 深海寄居蟹 | **完全不同** | 3027, 2257, 2139 |
| 1.0 | ① 巨型老面酵头　② 液态海　③ 盲眼纺织工 | 完全不同 | 1756, 2169, 1436 |
| 2.0 | ① 硅基珊瑚礁　② 玻璃蜘蛛　③ 玻璃胃珊瑚礁 | 完全不同（②③有"珊瑚/玻璃"意象交叉） | 3208, 2827, 1878 |

### 结论

1. **T=0 不是 100% 可复现**（验证了概念节知识点）：标准问题三次输出语义近似但措辞不同，说明 T=0 走 argmax 仍受浮点精度/模型版本/批处理效应影响
2. **T=0 的不一致程度与 prompt 类型相关**：标准问题 T=0 输出语义近似（模型对"人工智能定义"有强先验，top token logit 远超其他）；创意问题 T=0 输出**比喻主题完全不同**（候选词 logit 接近，微小的浮点差异更容易翻转 argmax，导致走向完全不同的创意方向）
3. **T=2.0 未出现乱码或偏离主题**：标准问题 T=2.0 仍输出标准定义；创意问题 T=2.0 仍输出连贯的创意比喻。推测原因：glm-5.2 可能对 temperature 有内部安全裁剪；中文常见表达（"是""的""了"等）logit 基础分极高，T=2.0 缩小差距后仍排前列
4. **temperature 效果是渐进的，不是二元切换**：从"0=完全确定 / 2=完全疯掉"的预期，到实际"0=略有波动 / 2=波动更大但仍连贯"，说明 temperature 是渐变旋钮，且效果受模型实现和 prompt 类型制约
5. **temperature 的效果是 prompt 相关的**：跨所有 temperature 值观察，标准问题输出始终相似、创意问题输出始终多样，说明 temperature 的可见效果受 prompt 类型制约--不能脱离 prompt 类型笼统说"temperature 高则随机性强"
6. **completion_tokens 变异度**：创意问题在所有 temperature 下的 token 变异度都大于标准问题，说明创意类任务本身就有更大的输出空间，temperature 放大了这个差异（创意 T=2.0 token 范围 1878~3208，跨度 1330）

## 实验记录：max_tokens 截断效果

> 产出脚本：`max_tokens_experiment.py` · 模型：glm-5.2
> 目的：验证 max_tokens 调小后对输出的截断效果

### 实验设计

问一个需要较长回复的问题，分别设置 max_tokens=10（故意极小）、2000（中等）、5000（充足），对比 finish_reason、content 和 completion_tokens。

```text
问题："详细解释 Python 的列表和元组的区别"
max_tokens 值：10, 2000, 5000
```

### 实验结果

| max_tokens | finish_reason | content | completion_tokens |
|---|---|---|---|
| 10 | `"length"` | 空（无输出） | 11 |
| 2000 | `"length"` | 部分输出（写到第 4 节中途断句："print(my_dict[(1, 2)]) #"） | 2001 |
| 5000 | `"stop"` | 完整回复（列表 vs 元组 6 个维度详解 + 总结表） | 2583 |

### 结论

1. **三组对比展示了推理模型 max_tokens 预算分配的三个阶段**：
   - **max_tokens=10**：预算 < 思考所需 -> 思考阶段就耗尽预算，正文未开始生成，content 为空
   - **max_tokens=2000**：预算 > 思考所需但 < 思考 + 完整正文 -> 思考完成，正文部分生成后截断，content 中途断句
   - **max_tokens=5000**：预算 > 思考 + 完整正文 -> 正常完成，finish_reason="stop"
2. **max_tokens 限制的是 reasoning + text 的总和**（验证了概念节知识点和 Day 4 的 reasoning_tokens 知识点）：不是只限正文，思考阶段也消耗预算
3. **completion_tokens 始终比 max_tokens 多 1**（10->11, 2000->2001）：推测 API 逐 token 检查，生成超出限制的 1 个 token 后才触发截断，是实现的边界细节
4. **max_tokens=2000 是最有价值的观察组**：它证明了"思考完成但正文未完成"的中间状态--content 不为空但中途断句，说明预算在 reasoning 和 text 之间是**顺序分配**的（先思考再生成正文），而非并行

> 关键发现：推理模型的 max_tokens 预算在 reasoning 和 text 之间顺序分配（先思考再正文）。预算太小->思考截断、正文为空；预算中等->思考完成、正文截断；预算充足->全部完成。调小 max_tokens 可能导致思考阶段就耗尽预算、正文完全为空。

## 参数场景建议（自测）

> 三个随机场景自测：给定场景，推荐 temperature、top_p、max_tokens 的取值
> 自测日期：2026-08-19

### 场景 1：法律合同翻译 API

用户上传英文法律合同，系统自动翻译成中文。合同条款的措辞必须精确，不能有歧义或多译。

| 参数 | 推荐值 | 理由 |
|---|---|---|
| temperature | 0 ~ 0.3 | 法律翻译需要精确性，低 temperature 保证措辞稳定、减少多译 |
| top_p | 1.0（默认） | temperature 已调低，按"二选一"原则 top_p 保持默认 |
| max_tokens | 设充足值（如 8192） | 不能不设（服务商默认可能仅 4K，长合同会被截断），也不能设太小 |

### 场景 2：RPG 游戏 NPC 对话生成器

为游戏中的酒馆老板生成日常对话，每天说不同的话，要有性格但不能出戏。

| 参数 | 推荐值 | 理由 |
|---|---|---|
| temperature | 0.7 ~ 1.2 | 需要多样性和创造力，让 NPC 每天说不同的话 |
| top_p | 1.0（默认） | temperature 已调高，按"二选一"原则 top_p 保持默认 |
| max_tokens | 适中（如 200~500） | NPC 对话不宜过长，限制输出长度避免发散和 token 浪费 |

### 场景 3：自然语言转 SQL 查询工具

用户输入"查上月销售额 Top 10 的客户"，系统根据数据库 schema 生成可执行的 SQL 语句。

| 参数 | 推荐值 | 理由 |
|---|---|---|
| temperature | 0 ~ 0.3 | SQL 语法和逻辑必须精确，低 temperature 减少语法错误 |
| top_p | 1.0（默认） | temperature 已调低，按"二选一"原则 top_p 保持默认 |
| max_tokens | 不设或设充足值 | SQL 语句通常长度可控，但不设时有服务商默认截断风险，建议设充足值 |

### 关键原则

1. **temperature 和 top_p 二选一**：调整 temperature 时 top_p 保持默认 1.0，反之亦然。同时调整会让效果不可预测、调试困难
2. **max_tokens 不设不等于不限制**：不设时使用服务商默认上限（通常远小于完整窗口），长输出可能被意外截断。建议根据任务预估输出长度设充足值
3. **为什么 temperature=0 适合需要确定性的任务**：temperature=0 时模型走 argmax，始终选择概率最高的 token，消除了采样的随机性，使输出尽可能稳定可复现
