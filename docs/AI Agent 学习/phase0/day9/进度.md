## Step 拆解

### Step 1 · 常见错误类型与 SDK 异常体系（类型：概念）

**前置依赖**：Day 8 的 llm_client_with_save_and_load.py（`chat` 里目前只有一个裸 `except Exception`，打印一条泛化信息）

**做什么**：
- 认识 openai SDK 的异常家族（都继承自 `openai.APIError`）：
  - `AuthenticationError`：401，Key 无效 / 过期
  - `RateLimitError`：429，请求过于频繁或配额用尽
  - `APIConnectionError` / `APITimeoutError`：网络不通 / 请求超时（后者是前者的子类）
  - `InternalServerError`：5xx，服务端问题
  - `BadRequestError`：400，参数错误（如 model 名写错）
- 建立**核心分类**，这是今天一切设计的地基：
  - 瞬时错误（重试可能好转）：超时、连接失败、429、5xx
  - 非瞬时错误（重试也没用，只会浪费时间）：无效 Key、余额不足、参数错误
- 了解一个厂商差异（记下来，面试可讲）："余额不足"不一定是独立异常——DeepSeek 用 HTTP 402，智谱塞在 429 的 message 里（错误码 1113），所以不能只看异常类名，要结合 message 判断

**参考资料**：
- openai-python 仓库 README 的 Error Handling 一节（GitHub: openai/openai-python）

**检查点**：
- 能说出 4 种常见错误各自的状态码、异常类名、典型成因
- 能回答"无效 Key 该不该重试，为什么"

**产出**：
- 笔记：记入 readme.md 的概念节

### Step 3 · 分类捕获，给出清晰提示（类型：编码）

**前置依赖**：Step 2 的错误观察表

**做什么**：
- 把 `chat` 里的裸 `except Exception` 升级为按异常类分类处理：
  - `AuthenticationError` -> 提示"API Key 无效，请检查 .env 中的 API_KEY"
  - `RateLimitError` / `APITimeoutError` / `APIConnectionError` -> 留给 Step 4 的重试逻辑
  - 其他异常 -> 打印原始错误信息（未知错误不吞细节）
- 注意 except 的书写顺序：子类要放在父类前面（`APITimeoutError` 是 `APIConnectionError` 的子类），否则永远不会被精确捕获
- 保持对外接口不变：失败时仍返回 `None`
- 跑一次"填错 Key"场景验证：不崩溃、提示能直接指导用户去改哪里

**检查点**：
- 填错 Key 时：程序不崩溃，报错信息明确指向 `.env`（完成标志的一半）
- 填正确 Key 时：Day 8 的多轮对话 + save/load 流程回归通过（改坏老功能是重灾区）

### Step 4 · 简单重试逻辑（类型：编码）

**前置依赖**：Step 3 的分类捕获

**做什么**：
- 只对瞬时错误重试（超时 / 连接失败 / 429），非瞬时错误直接走 Step 3 的分类提示
- 实现要点（不引第三方库，手写循环即可）：
  - 参数：`max_retries=3`
  - 每次重试前 `time.sleep()`，先固定 1 秒；有余力再改成 1s / 2s / 4s 的指数退避
  - 每次重试打印一行日志：第几次重试、原因是什么
- 验证方法：把 `timeout` 调小到必然失败 + `max_retries=2`，观察先打印 2 次重试日志、再走分类提示、最后优雅返回 `None`

**检查点**：
- 重试只发生在可重试的错误上，无效 Key 不会触发重试
- 重试达到上限后程序不崩溃，行为可预期
- 能说清为什么重试间隔要"越等越久"而不是固定 0.1 秒连打

**产出**：
- 文件：`llm_client_with_retry.py` 更新（自写，写完贴给 AI review）
