```text
  ├── 提示词约束对"过时信息"幻觉无效               ←── 串联 Day 3：system prompt 约束力是概率性的
  └── RAG 插入"事实校验"步骤，打在根因上            ←── 预习阶段 3
```

**关键认知**：

1. **一条主线贯穿全周**：LLM 是概率预测器 -- Day 3 的"无状态"是因为每次请求独立预测、Day 4 的"复利计费"是因为要重发全部历史、Day 5 的"采样参数"是控制预测时的选择方式、Day 6 的"幻觉"是概率预测没有事实校验的必然副产物
2. **"记忆"和"幻觉"都不是模型的能力或缺陷，而是概率预测机制的投影**：记忆是工程拼回历史的"效果"，幻觉是缺少事实校验的"代价"
3. **system prompt 的约束力是概率性的** -- 这条认知在 Day 3 实验 4 发现，在 Day 6 实验中得到致命验证（提示词约束对"过时信息"幻觉无效，因为模型不认为自己是"不确定"的）
4. **每个参数/概念都有"管什么"和"不管什么"的边界**：temperature 管"怎么选"不管"知不知道"，top_p 管"候选池"不管"分布形状"，max_tokens 管"多长"不管"质量"，RAG 管"拿什么选"不管"怎么选"

> 一句话：Day 1-6 的所有知识可以收敛为一句 -- LLM 是概率预测器，无状态、无记忆、无事实校验，一切"智能"表现都是工程在这台预测器外围搭建的效果。

## 自测

1. **能解释 token、上下文窗口、幻觉、temperature 的含义？**
   - **token**：模型处理和计费的最小文本片段，tokenizer 按 vocab 切出来的产物；常见组合整个当一个 token，罕见组合被拆碎，中文因词表偏英文 + UTF-8 编码而更贵
   - **上下文窗口**：模型一次请求能处理的最大 token 数（输入+输出总和），是模型架构层面的硬上限，超限请求阶段报错或生成阶段截断
   - **幻觉**：模型生成看似合理但实际不正确/虚构的内容；根因是概率预测没有事实校验步骤，模型永远会输出，不区分"知道"和"生成"
   - **temperature**：采样参数，作用在 logits 上（softmax 之前）缩放原始分数差距；T 小则分布尖锐（确定性高），T 大则分布平坦（随机性强）；不改变模型"知道什么"，只改变"怎么选"

2. **能说清 system / user / assistant 三种角色的区别？**
   - **system**：开发者设定，全局指令（人设/格式/边界/流程），通常放 messages 第 0 条，优先级高但约束力是概率性的
   - **user**：最终用户的提问/指令，数量和顺序无限制
   - **assistant**：模型的历史回复，**由你的代码负责拼回 messages**，服务器不保存对话历史（无状态 API）

3. **为什么每次请求都要传完整历史？**
   - Chat API 是无状态的：服务器处理完请求就忘掉一切。模型每轮"知道"什么，完全取决于本次请求的 messages 里装了什么。不传历史，模型当全新问题处理；传完整历史，模型才能"读懂"对话脉络

4. **temperature=0 为什么不是 100% 可复现？**
   - 非确定性发生在前向传播（logits 计算）阶段而非采样阶段。T=0 保证"给定相同 logits 选 argmax"，但不保证"两次请求算出相同 logits"（浮点精度、模型版本、批处理效应导致微小差异）

5. **缓解幻觉的五种手段分别对应解决哪个成因？**
   - 提示词约束 -> prompt 措辞引导、长尾知识（对"过时信息"无效，模型不知道自己过时）
   - 降低 temperature -> 概率预测本质（采样随机性，不改变"知不知道"）
   - RAG -> 训练数据截止时间、长尾知识、数据质量（插入"事实校验"步骤，打在根因上）
   - 结构化输出 -> 概率预测本质（让用户区分检索内容和模型推测）
   - 多次采样投票 -> 概率预测本质（代价是成本翻倍，对"模型确信的错误答案"无效）

6. **temperature 和 top_p 有什么关系？为什么不建议同时调整？**
   - temperature 改变分布形状（缩放 logits），top_p 改变候选池范围（截断概率）；两者串行执行（temperature 先缩放，top_p 再在新分布上截断），同时调整会让效果不可预测、调试困难、可能互相抵消

## 本节记住五件事

1. **一条主线**：LLM 是概率预测器 -- 无状态、无记忆、无事实校验，"记忆"和"幻觉"都是这个机制的投影
2. **三角色分工**：system 设全局（约束力是概率性的），user 提问，assistant 由代码拼回（无状态 API 的直接后果）
3. **token 是最小单位**：计费、上下文窗口、成本估算都以 token 为单位；中文更贵（词表偏英文 + UTF-8 编码）
4. **三个参数各管一边**：temperature 管"分布形状"，top_p 管"候选池范围"，max_tokens 管"输出长度" -- 二选一原则
5. **幻觉缓解要对症下药**：没有银弹，提示词约束对"过时信息"无效，RAG 打在根因上（插入事实校验步骤）

## 查漏攻坚：三项"模糊"知识点

> 来源：Step 1 概念分类中标记为"模糊"的三项 · 目的：逐个攻克，降为"已掌握"

### 模糊项 1：LLM vs 传统软件的区别（Day 1 概念补遗）

> 来源：Day 1 任务要求"问 AI：大语言模型是怎么生成文字的、它和传统软件有什么区别"，但 Day 1 笔记仅有安装命令，概念未记录 · 本节补遗

传统软件和 LLM 的根本差异在于**工作方式**：传统软件是"规则驱动"，开发者把逻辑写成 if-else；LLM 是"概率驱动"，模型基于上文预测下一个 token。

| 对比维度 | 传统软件 / 数据库 | LLM |
|---|---|---|
| 工作方式 | 查询知识库，匹配记录返回 | 预测概率最高的文字序列 |
| 输出确定性 | 确定：相同输入永远相同输出 | 概率性：相同输入可能不同输出（temperature > 0） |
| 找不到答案时 | 返回"查不到" | 仍生成"看起来像答案"的文字（幻觉） |
| 事实校验 | 有（查询结果可验证） | 无（生成流水线没有事实校验步骤） |
| 调试方式 | 逐步调试逻辑，可定位到具体代码行 | 无法逐行调试，只能调 prompt / 参数 / 换模型 |
| 正确性保证 | 可做到 100% 正确（逻辑无误即正确） | 无法保证 100% 正确（概率预测的必然代价） |

```text
传统软件：用户提问 -> 查询知识库 -> 有记录 -> 返回结果
                                  └-> 无记录 -> 返回"查不到"

LLM：     用户提问 -> 拼接上下文 -> 逐 token 预测概率最高的文字 -> 输出
                                          ↑
                                   没有"事实校验"这一步
                                   训练数据见过 -> 大概率答对
                                   训练数据没见过 -> 仍生成"像答案"的话（幻觉）
```

**关键认知**：

1. **传统软件"查询"，LLM"生成"**：传统软件从知识库中检索匹配记录，LLM 基于上文逐 token 预测概率最高的文字序列 -- 这是理解后面所有概念（无状态、幻觉、采样参数）的根基
2. **"查不到"vs"编一个"**：传统软件找不到就返回空，LLM 没有空状态，永远会输出 -- 这就是幻觉的根源
3. **确定性 vs 概率性**：传统软件相同输入永远相同输出，LLM 即使 temperature=0 也受浮点精度影响无法 bit 级复现（Day 5 实验验证）

> 一句话：传统软件是"查到就答、查不到就说没有"，LLM 是"永远生成最像答案的文字" -- 一个查询，一个预测，这是所有差异的起点。

### 模糊项 2：独立写出完整 API 调用代码（实践技能验证）

> 来源：验收清单第 2 项"不看示例，能独立写出完整的 API 调用代码" · Step 1 自测仅覆盖概念理解，实践技能未验证

**代码必须包含的 7 个要素**：

| 序号 | 要素 | 说明 | 漏写后果 |
|---|---|---|---|
| 1 | `import` 语句 | `os`、`dotenv` 的 `load_dotenv`、`openai` 的 `OpenAI` | 无法使用环境变量和 SDK |

**对照参考**（基于 [Day 2 的 hello_llm.py](../day2/hello_llm.py)）：

```python
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()

client = OpenAI(
    base_url=os.getenv("BASE_URL"),
    api_key=os.getenv("API_KEY"),
)

try:
    response = client.chat.completions.create(
        model="deepseek-v4-flash",
        messages=[
            {"role": "system", "content": "你是一个毒舌但心软的助手，回答末尾总要补充一句关心。"},
            {"role": "user", "content": "我今天学习进度落后了，很焦虑。"},
        ]
    )

    print(response.choices[0].message.content)
except Exception as e:
    print(e)
```

### 模糊项 3：两个"易混淆"概念复查

> 来源：Day 5 和 Day 6 笔记自身标注的"容易混淆"概念 · 目的：脱稿说清两者的区别

#### 易混淆 A：模型最大输出限制 vs 服务商默认上限

两个都是"上限"，但一个是模型架构天花板，一个是不设参数时的自动值：

| 对比维度 | 模型最大输出限制 | 服务商默认上限 |
|---|---|---|
| 是什么 | 模型单次能生成的**绝对上限** | 不设 max_tokens 时服务商自动使用的值 |
| 谁决定 | 模型架构 | 服务商配置 |
| 能突破吗 | 不能，max_tokens 超过它直接报错 | 能，显式设 max_tokens 即可覆盖 |
| 大小关系 | 通常远小于上下文窗口 | 可能等于模型最大输出，也可能远小于它 |
| 不设 max_tokens 时 | 不设也受此上限约束 | 生效：用这个值截断输出 |

```text
举例（假设值）：
  上下文窗口：       128K（输入+输出的总和上限）
  模型最大输出限制：  8K（天花板，max_tokens 不能超过它）
  服务商默认上限：   4K（不设 max_tokens 时自动用这个值）

三种情况：
  max_tokens=2K    -> 2K < 8K 且 2K < 1014K  -> 生成到 2K 截断
  max_tokens=10K   -> 10K > 8K              -> 报错（超过天花板）
  不设 max_tokens   -> 用服务商默认 4K 截断（可能意外截断长输出）
```

> 一句话：模型最大输出是"天花板"（不能突破），服务商默认是"不设时的自动值"（可能远低于天花板） -- 不设 max_tokens 不等于"不限制"。

#### 易混淆 B：长尾知识 vs 长尾 token

名字里都有"长尾"，但一个是幻觉成因，一个是采样效果，作用阶段完全不同：

| 对比维度 | 长尾知识 | 长尾 token |
|---|---|---|
| 是什么 | 冷门领域在训练数据中出现次数少 | 低概率 token 在采样时被选中 |
| 作用阶段 | 生成阶段（模型先验弱 -> 概率分布平缓） | 采样阶段（temperature 缩放后低概率 token 获得机会） |
| 是什么的问题 | 知识问题（模型没学过） | 采样问题（选了不该选的 token） |
| 导致什么 | 幻觉（编造看起来像答案的内容） | 乱码或偏离主题（选了荒谬的 token） |
| 对应缓解手段 | RAG（补外部知识） | 降低 temperature（减少低概率 token 被选中的机会） |
| 关联参数 | 与 temperature 无关 | 与 temperature 直接相关 |

```text
长尾知识（幻觉成因）：
  冷门领域训练数据少 -> 模型先验弱 -> 概率分布平缓
  -> 更容易生成"看起来像答案但实际编造"的内容
  -> 这是"模型不知道"的问题，temperature=0 也答不对

长尾 token（temperature 效果）：
  低概率 token 在高 temperature 下被选中 -> 采样随机性
  -> 可能导致乱码或偏离主题
  -> 这是"模型知道但选错了"的问题，降 temperature 能缓解
```

> 一句话：长尾知识是"训练数据不够导致模型先验弱"（幻觉成因，RAG 解决），长尾 token 是"采样时低概率词被选中"（temperature 效果，降 T 解决） -- 前者是"不知道"，后者是"选错了"。

**关键认知**：

1. **模型最大输出限制是天花板，服务商默认是自动值**：不设 max_tokens 不等于"不限制"，而是用了服务商可能远低于天花板的默认值
2. **长尾知识和长尾 token 作用阶段不同**：前者在生成阶段（模型先验弱导致幻觉），后者在采样阶段（低概率 token 被选中导致乱码）
3. **两者对应的缓解手段不同**：长尾知识用 RAG 补知识，长尾 token 用降 temperature 减少随机性 -- "不知道"和"选错了"是不同的问题

> 一句话：两个"易混淆"的本质都是"分清作用阶段" -- 模型最大输出限制管"能生成多少"（架构层面），服务商默认管"不设时用多少"（配置层面）；长尾知识管"先验强弱"（训练层面），长尾 token 管"采样随机性"（推理层面）。

## 查漏自测

1. **LLM 和传统软件回答问题的机制有什么本质区别？**
   - 传统软件"查询"知识库，找到匹配记录返回，找不到返回"查不到"；LLM"生成"概率最高的文字序列，永远会输出，没有"查不到"状态
   - 本质区别：一个查询、一个预测；一个有事实校验、一个没有

2. **不看示例，能独立写出完整的 API 调用代码吗？**
   - 7 个要素：import / load_dotenv / 创建客户端 / create 调用 / messages（system+user）/ 取 choices[0].message.content / try-except
   - API Key 从 `os.getenv` 读取而非硬编码（安全 + 环境切换）

3. **模型最大输出限制和服务商默认上限有什么区别？**
   - 模型最大输出限制是架构天花板，max_tokens 不能超过它（超过报错）；服务商默认上限是不设 max_tokens 时的自动值，可能远低于天花板
   - 不设 max_tokens ≠ 不限制，而是用了服务商默认值，可能意外截断长输出

4. **长尾知识和长尾 token 有什么区别？**
   - 长尾知识是冷门领域训练数据少导致模型先验弱（幻觉成因，RAG 解决）；长尾 token 是低概率 token 在高 temperature 下被选中（采样效果，降 T 解决）
   - 前者是"不知道"的问题，后者是"选错了"的问题

## 查漏记住三件事

1. **LLM vs 传统软件**：查询 vs 生成，"查不到" vs "编一个" -- 这是幻觉、无状态、概率性输出的共同根源
2. **独立写 API 代码**：7 个要素缺一不可（import / load_dotenv / 客户端 / create / messages / 取 content / 异常处理）
3. **两个易混淆已澄清**：模型最大输出限制（天花板）vs 服务商默认（自动值）；长尾知识（幻觉成因）vs 长尾 token（采样效果）
