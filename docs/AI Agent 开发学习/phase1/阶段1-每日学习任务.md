## 第 1 周：Prompt 工程与结构化输出

> 本周主线：先掌握"把话说清楚"的三大技巧（角色设定 / few-shot / CoT），再解决"让模型输出程序能消费的数据"（JSON mode + Pydantic 校验），周末组装出信息抽取 demo v1。

### Day 1 · Prompt 工程总览与角色设定（约 1h）

**目标**：建立 prompt 工程的知识地图；掌握最常用的角色设定（role prompting），并用对比实验验证效果。

**步骤**：
- 通读一份官方 prompt 指南（推荐 DeepSeek 官方提示词指南，或 OpenAI Prompt Engineering 指南的策略篇），用 10 分钟整理出核心技巧清单：清晰具体指令、角色设定、少样本示例、思维链、结构化输出、分隔符
- 用 LLMClient 跑两组对比实验，每组至少跑 2 次，从四个维度记录差异：专业性、格式、语气、内容深度
  - 任务 A（技术向）：贴一段 Python 报错让模型解释，分别用"无角色设定"和"你是十年经验的 Python 排错专家"
  - 任务 B（文风向）：写一条无线耳机推广文案，分别用"普通助手"和"你是小红书爆款写手"
- 把每组的 prompt 与输出摘要记入笔记，标注差异最明显的一处

**产出**：角色设定对比实验记录（2 组任务 × 2 种角色 × 各 ≥2 次）

- [ ] ✅ 完成标志：能说出 3 条以上 prompt 工程核心原则，并能举一个实测中"角色设定明显提升输出质量"的案例

### Day 2 · 少样本示例 few-shot（约 1h）

**目标**：掌握 few-shot 的用法与适用场景，理解"示例即规范"。

**步骤**：
- 概念辨析：zero-shot / one-shot / few-shot 的区别；什么任务必须给示例（输出格式敏感、任务生僻、领域特殊）
- 设计一个固定任务：用户评论情感分类（输出：标签 + 置信度），准备 5 条测试输入，其中故意放 1 条难分辨的（如反讽）
- 对比实验：同一批输入分别用 0 示例 / 1 示例 / 3 示例各跑一遍，记录两个指标：输出格式是否稳定、分类结果是否一致
- 进阶观察：故意让 3 个示例格式不统一（标签中英文混用、字段顺序不同），看输出如何被"带偏"——体会示例的格式会被模型严格模仿

**产出**：few-shot 对比实验记录（0/1/3 示例 × 5 条输入）

- [ ] ✅ 完成标志：能说清什么任务必须用 few-shot、示例设计要注意什么（格式统一、覆盖边界情况）

### Day 3 · 思维链 CoT（约 1h）

**目标**：理解 CoT 的原理与适用边界，建立"效果—成本"权衡意识。

**步骤**：
- 概念：CoT 为什么有效（引导模型先产出中间推理步骤再下结论）；两种形式——zero-shot CoT（"请一步步分析"）与 few-shot CoT（示例中带推理过程）；CoT 的 token 成本代价
- 准备 3 道测试题：数学应用题、逻辑推理题、简单事实题各一
- 对比实验：每道题分别"直接问"和"要求一步步分析再给答案"，用 LLMClient 的 usage 统计记录答案正确性与 completion tokens
- 观察：事实题加 CoT 是否纯属浪费 token？数学/逻辑题正确率是否提升？
- 思考记入笔记：推理类任务为什么建议搭配低 temperature

**产出**：CoT 对比实验记录（3 题 × 2 种问法 + token 消耗对比表）

- [ ] ✅ 完成标志：能回答"CoT 什么场景值得开、什么场景是浪费"

### Day 4 · Prompt 模板化与综合实战（约 1.5h）

**目标**：把角色设定 + few-shot + 输出格式规范组合成可维护的 prompt 模板——这是信息抽取 demo 的直接前置。

**步骤**：
- 选一个综合实战任务（二选一，后续 demo 直接复用）：
  - 客服意图分类器：输入用户消息 → 输出 意图 / 紧急程度 / 建议回复
  - 产品评论信息抽取：输入评论 → 输出 产品 / 问题类型 / 情感 / 是否建议购买
- 写 v1 版 prompt：角色设定 + 3 个 few-shot 示例 + 明确的输出格式说明（本阶段暂用简单 JSON 或固定表格，Day 5 再升级 JSON mode）
- 学习把 prompt 模板化：用 Python f-string 把"任务说明 / 示例 / 用户输入"拆成变量，封装成 `build_prompt(user_input)` 函数，加版本号注释——像管理代码一样管理 prompt
- 用 5 条新输入测试 v1，记录失败案例，迭代出 v2（改了哪里、为什么改、效果变化）

**产出**：v1/v2 两版 prompt 模板（`build_prompt` 函数）+ 迭代记录

- [ ] ✅ 完成标志：模板函数在 5 条新输入上输出格式 100% 稳定

### Day 5 · JSON mode 结构化输出（约 1h）

**目标**：让模型输出 100% 可被 `json.loads` 的 JSON；理解 JSON mode 的能力边界。

**步骤**：
- 概念：为什么下游程序需要结构化输出；"prompt 里要求输出 JSON"与 JSON mode 的本质区别
- 给 LLMClient 增加 `json_mode` 参数：透传 `response_format={"type": "json_object"}`（注意 DeepSeek 的约束：prompt 中必须出现 "json" 字样才生效，写进踩坑记录）
- A/B 对比实验（同一抽取任务）：
  - A 组：仅在 prompt 里要求输出 JSON，不开 JSON mode
  - B 组：开启 JSON mode
  - 各跑 5 次，统计 `json.loads` 成功率
- 建立踩坑记录（每遇到一条记一条）：markdown 代码块包裹、字段名漂移（`name` vs `姓名`）、必填字段缺失
- 关键认知：JSON mode 只保证"语法合法"，不保证"内容正确"（字段缺失、幻觉仍在）——为 Day 6 的 Pydantic 语义校验做铺垫

**产出**：LLMClient 支持 json_mode + A/B 实验记录

- [ ] ✅ 完成标志：B 组 5/5 解析成功；能说清 JSON mode 保证什么、不保证什么

### Day 6 · Pydantic 解析与校验（约 1.5h）

**目标**：用 Pydantic 给结构化输出上"类型保险"，实现校验失败自动重试闭环。

**步骤**：
- Pydantic 速成（约 30 分钟，够用即可）：`BaseModel` 定义、常用字段类型（str/int/float/list/嵌套模型）、`Optional` 与默认值、`Field(description=...)` 对模型的提示作用
- 把 Day 4 的抽取任务输出用 Pydantic 定义为 `ExtractResult`（含嵌套结构，如 `list[str]` 技能列表）
- 实现 `parse_and_validate(text)`：`json.loads` → `ExtractResult.model_validate`
- 实现校验失败兜底闭环：捕获 `ValidationError` → 把错误信息拼进新 prompt（"你上次的输出缺少必填字段 xxx，请重新输出完整 JSON"）→ 重新请求，最多重试 2 次
- 故意破坏测试：手动构造 3 种坏输出（缺字段 / 类型错误 / 嵌套结构错误），验证兜底逻辑都能处理

**产出**：schema 定义 + 解析校验模块（约 80-100 行，含重试闭环）

- [ ] ✅ 完成标志：3 种构造的非法输出全部被兜底修复或明确报错，程序不崩溃

### Day 7 · 周复盘 + 信息抽取 demo v1（约 1.5h）

**目标**：复盘第 1 周概念；组装完成【产出二】的 v1 版本。

**步骤**：
- 闭卷复盘自问（答不上的翻笔记、问 AI）：角色设定 / few-shot / CoT 各解决什么问题？JSON mode 与 prompt 约束的区别？校验失败重试闭环的原理？
- 组装信息抽取 demo v1：输入一段自然语言（新闻/评论）→ JSON mode + Pydantic 校验 → 输出结构化 JSON；支持读取 txt 文件批量逐条处理
- 建立项目骨架：`projects/extractor/`——`schema.py`（Pydantic 定义）、`parser.py`（解析校验）、`main.py`（入口）、`examples/`（3 条示例输入）
- 跑 5 条示例输入全部输出合法 JSON 后，`git init` + 首次提交

**产出**：信息抽取 demo v1（自然语言 → 校验通过的 JSON，支持批量）

- [ ] ✅ 完成标志：5 条示例输入全部成功输出合法 JSON；仓库有首次提交

## 第 2 周：Function Calling 核心流程

> 本周主线：打通 Agent 的基石——Function Calling 完整五步闭环，接入 3 个真实工具，整合出命令行助手 v1 并做健壮性强化。这是阶段 2 手写 Agent 的直接地基，务必扎实。

### Day 8 · Function Calling 初体验（约 1h）

**目标**：理解 FC 存在的意义；第一次亲眼观察到模型"决定调用工具"。

**步骤**：
- 概念：FC 解决什么问题——让模型"声明要执行的动作"而不是"硬编答案"，执行权始终在我们代码手里（对比 Day 5 纯 prompt 约束输出 JSON 的脆弱性）
- 精读官方文档的 Function Calling 章节（DeepSeek 或 OpenAI 的，两者请求格式兼容），重点看：请求中 `tools` 参数的结构、响应中 `tool_calls` 的结构
- 写最小 demo（约 40 行）：
  - 定义 `get_current_weather` 工具（JSON Schema：参数 `city`，string，必填），函数体先返回假数据
  - 发送"北京今天天气怎么样"，打印完整响应 JSON
  - 逐字段标注含义：`finish_reason="tool_calls"`、`message.tool_calls[0].function.name` 与 `.arguments`
- 对比实验：问一个不需要工具的问题（"1+1 等于几"），观察模型直接回答、不产生 tool_calls

**产出**：FC 最小 demo 脚本 + tool_calls 响应结构注解笔记

- [ ] ✅ 完成标志：能对照响应 JSON 说出每个关键字段的作用；能说清 FC 与"让模型输出 JSON 自己解析"的区别

### Day 9 · 完整调用闭环（约 1.5h）

**目标**：亲手实现 FC 完整五步：**定义 → 决策 → 执行 → 回填 → 再生成**。

**步骤**：
- 实现 `run_with_tools(messages)` 函数：
  1. 请求携带 tools 定义
  2. 收到 tool_calls：解析 name 和 arguments（注意 arguments 是 JSON 字符串，需 `json.loads`）
  3. 本地执行对应函数（此阶段仍只有天气假数据工具）
  4. 把执行结果以 `role="tool"` + `tool_call_id` 追加进 messages；注意 assistant 的 tool_calls 消息也必须原样追加（消息链完整性——建议故意漏掉一次，亲眼看报错，理解为什么）
  5. 再次请求，拿到最终自然语言回答
- 画流程图（手画或 mermaid）：用户输入 → 模型决策（调/不调）→ 执行 → 回填 → 模型生成回答
- 实验：让天气工具返回"城市不存在"的错误文本，观察模型如何向用户转述失败

**产出**：`run_with_tools` 函数（约 50-80 行）+ 闭环流程图

- [ ] ✅ 完成标志：完整跑通"提问 → 调工具 → 回填 → 回答"闭环；能脱稿讲清五步和 tool_call_id 的作用

### Day 10 · 多工具注册与工具设计（约 1.5h）

**目标**：接入 3 个真实工具；建立"description 就是给模型看的说明书"的设计意识。

**步骤**：
- 实现 3 个真实工具：
  - 天气查询：用 requests 调 wttr.in（`https://wttr.in/{city}?format=j1`，免注册返回 JSON；不稳定时换 Open-Meteo，同样免 key）
  - 计算器：算术表达式求值——用 `ast` 模块实现安全求值，只放行数字与加减乘除幂节点；明确禁止裸 `eval`（想清楚为什么：能被注入 `__import__('os')...` 之类的代码）
  - 文件读写：`read_file` / `write_file`，只允许访问 `./sandbox/` 目录内的文件（最简单的权限边界，思考为什么不能放开全盘路径）
- 设计统一注册结构：每个工具 = Python 函数 + `{name, description, parameters(JSON Schema)}`，集中由一个 `TOOLS` 列表管理
- 工具选择实验（5 条混合提问）："帮我算 35*89+12" / "上海周末适合出游吗" / "把我刚才的结论记到 notes.txt" / "现在几点了"（无对应工具，看模型是否老实承认） / 一条需要两个工具配合的问题
- 对比实验：把天气工具的 description 改得含糊，重测选择准确率——用数据证明 description 质量 = 工具选择准确率

**产出**：3 个真实工具 + 统一注册结构 + 两组工具选择实验记录

- [ ] ✅ 完成标志：5 条混合提问工具选择 ≥4 次正确；description 好坏对比有实测数据

### Day 11 · 工具调用的错误处理（约 1.5h）

**目标**：让调用链条"打不死"：非法参数自动修正、执行异常不崩溃、支持多轮工具循环。

**步骤**：
- 场景 1 · 模型返回非法参数：
  - 执行前用 Pydantic 校验入参（每个工具的参数 schema 沿用 Day 6 的定义方式）
  - 校验失败不抛异常，而是把"参数错误：city 为必填"作为 tool 结果回填，让模型自我修正——这是阶段 2 Agent 自愈机制的雏形
  - 实验：给一条含糊指令诱导模型犯参数错误，观察自动补正过程
- 场景 2 · 工具执行异常：每个调用包 try/except，异常文本同样回填给模型；天气等网络请求加 `timeout=10`
- 场景 3 · 多轮工具循环：把 `run_with_tools` 改成 while 循环——持续处理 tool_calls 直到模型不再调用工具；加 `max_steps=10` 上限（死循环防护，阶段 2 深化为正式的终止条件设计）
- 验证实验："对比北京和上海的天气"应触发连续两次工具调用

**产出**：`run_with_tools` v2（参数校验 + 异常回填 + 多轮循环 + 步数上限，约 120 行）

- [ ] ✅ 完成标志：三类错误场景均不崩溃且模型能自我修正；多轮工具调用实测跑通

### Day 12 · 命令行助手 v1 整合（约 2h）

**步骤**：

  - 继承阶段 0 能力：API 错误重试、历史保存/加载（扩展为支持 tool 消息）、token 统计

- 记录 3 个"模型行为不符合预期"的案例与处理方式（如：不调工具硬编答案、编造不存在的城市参数）

**产出**：命令行助手 v1（可运行）

- [ ] ✅ 完成标志：连续 10 轮混合对话无崩溃；历史保存后重新加载能继续对话

### Day 13 · 健壮性强化与边界测试（约 1h）

**目标**：系统化补齐总计划【必须】的错误处理项；建立边界测试习惯。

**步骤**：
- 对照边界清单逐项实测并修复：
  - 断网 / 错误 API Key / 余额不足：错误信息清晰、程序不崩溃
  - rate limit（429）：在阶段 0 重试基础上加指数退避（1s / 2s / 4s）
  - 模型输出非 JSON 的极端情况：用正则提取 `{...}` 片段兜底，仍失败则降级为普通对话
  - 工具返回超长内容：截断到约 2000 字符再回填（想清楚为什么：上下文预算 + 无意义的 token 浪费）
