### Step 2 · 角色设定 role prompting 专题（类型：概念）

**前置依赖**：Step 1 的技巧清单

**做什么**：
- 弄清角色设定的两种放置位置：system prompt（推荐，全局稳定）vs user prompt 开头（临时注入）；本日实验通过 LLMClient 构造参数 `system_prompt` 传入
- 理解为什么有效：角色收窄了模型输出 distribution 的"人格 / 词汇 / 视角 / 格式"先验，相当于隐式圈定了语料风格
- 明确适用边界：哪些任务收益大（专业领域解释、特定文风写作），哪些几乎无感（简单事实题、闲聊）

**参考资料**：
- DeepSeek / OpenAI 指南中关于 system message 与角色设定的部分
- 可问 AI："角色设定放在 system 和放在 user 消息里有什么区别？为什么任务型场景推荐放 system？"

**检查点**：
- 能回答"角色设定为什么有效"（用分布/先验的角度说，不背书）
- 能说出角色设定收益大和无感的任务类型各一个

### Step 3 · 实验准备：材料 + 脚本 + 记录表（类型：实验/编码）

**前置依赖**：阶段 0 的 LLMClient（`projects/llm_client`，角色入口为构造参数 `system_prompt`）

**做什么**：
- 固定实验材料：
  - 任务 A 输入：一段真实的 Python Traceback（自己制造，如 `KeyError` / `TypeError`，报错信息必须真实，不要手编假的）
  - 任务 B 输入：一条无线耳机推广文案需求（固定产品卖点，如"降噪、续航 30 小时、售价 299"）
- 写脚本 `role_experiment.py`：外层循环 2 任务 × 2 角色 × 各 2 次 = **8 次调用**；两种角色使用**同一份 user prompt，只改 system_prompt**（单变量原则）
- 设计四维度记录表（每次调用填一行）：专业性 / 格式 / 语气 / 内容深度

**关键细节（两个必踩的坑，先想清楚再写代码）**：
1. **每次调用都新建 `LLMClient` 实例**，原因有二：
   - `system_prompt` 只能在构造时传入，切角色必须换实例
   - `chat()` 会把每轮问答累积进 `self.messages`，同一实例第二次调用能看到前一轮输出，污染实验（模型可能回答"如前所述…"）
2. **基线组不能依赖默认 system_prompt**：LLMClient 默认值是"回答不超过 300 个字符、直接精简"——这是主动约束，会把两组的"内容深度"差异同时压平。基线组必须显式传入中性设定（如"你是一个乐于助人的助手"）

**检查点**：
- 脚本能一次跑完 8 次调用并完整保存 8 份原始输出（打印或落盘均可）
- 能脱稿说清：为什么要每次新建实例、为什么基线组要覆盖默认 system_prompt

**产出**：
- 代码：`role_experiment.py`（自写，写完贴给 AI review）
- 踩坑：若实验中观察到默认 system_prompt 的影响，记入 readme.md 踩坑记录（现象 / 原因 / 解决）

### Step 4 · 实验：任务 A · 技术向（类型：实验）

**前置依赖**：Step 3 的脚本与材料

**做什么**：
- A0 组：中性助手 system_prompt + Python 报错输入，跑 **≥2 次**
- A1 组：`"你是十年经验的 Python 排错专家"` + 同一份报错输入，跑 **≥2 次**
