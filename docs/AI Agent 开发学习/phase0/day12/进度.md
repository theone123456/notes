## Step 拆解

### Step 1 · 仓库边界与项目结构四问（类型：思考）

**前置依赖**：Day 11 的全部产出（类、CLI、11 用例测试套件——今天整理的原材料）；Day 10 的 report / Day 11 的设计节与实验记录（README 的素材已经在里面）

**做什么**：
- 动工前先定方案（沿用 Day 8 / Day 11 的做法，结论写进 readme.md 的项目设计节），回答四个设计问题：
  1. **仓库边界**：在哪 `git init`？两个候选：
     - A. 新建独立项目目录（如 `Development/llm_client/`），只放整理后的代码 + README + docs/ ——干净，求职导向（推荐）
     - B. 直接在 `Development/` init ——学习过程、`.env`、`.venv` 全在旁边，历史混杂且风险高
     - 依据：阶段 2 产出要求"整理成规范的 GitHub 仓库"、阶段 6 要求"仓库规范化"——今天建的是**求职项目的地基**，不是学习过程存档；学习笔记 Day 14 才以 `docs/` 形式有选择地进仓库
  2. **文件拆分**：拆成什么结构？给一个候选（可自行调整）：

     ```text
     llm_client/                 # 仓库根
     ├── llm_client/             # 包
     │   ├── __init__.py         # 空文件或 re-export LLMClient
     │   ├── client.py           # LLMClient 类（被 import 的库）
     │   └── cli.py              # 命令行界面（程序本体）
     ├── tests/
     │   └── test_cli.py         # 回归资产
     ├── pytest.ini
     ├── .gitignore
     ├── .env.example            # 只有变量名，没有值
     ├── README.md
     └── docs/                   # Day 14 学习笔记预留位
     ```

     拆分原则：一个文件一个职责——**类（库）、界面（本体）、测试（防线）** 三类性质不同的代码分开放。Day 11 已经打过样（`chat_cli.py` 只放界面逻辑，为今天铺的路）
  3. **什么不进库**：逐个决定并写明理由——`.env`（真实 Key，一旦公开被爬虫扫走就是别人的算力）、`.venv/`（环境不属于代码）、`__pycache__/` `.pytest_cache/`（生成物）、`history.json`（个人对话内容）。配套动作：提供 `.env.example`，仓库可用且安全
  4. **README 的读者**：定读者才能定详略。建议：面试官/其他开发者，30 秒看懂"这是什么、怎么跑起来"；学习过程叙事（为什么这么设计、踩过什么坑）留给 `docs/`

**检查点**：
- 能说出为什么 `.gitignore` 必须在首次提交**之前**就位，而不是提交后再补
- 能一句话说清拆分后每个文件的职责
- 四问都有明确答案和理由

**产出**：
- 笔记：设计结论记入 readme.md 的项目设计节

### Step 2 · 拆分文件 + 补关键注释 + 回归验证（类型：编码）

**前置依赖**：Step 1 的结构结论

**做什么**：
- 按定稿结构重组 day11 三件套（**复制过去改，day11 原样保留作对照**）：
  - `client.py`：`LLMClient` 类迁入；`chat_cli.py` 里的 `from llm_client_with_usage import LLMClient` 相应改为包内引用
  - `cli.py`：界面逻辑迁入；运行方式从 `python chat_cli.py` 变为 `python -m llm_client.cli`
  - `tests/test_cli.py` + `pytest.ini`：迁入，`CHAT_CLI` 路径、`ENV_FILE` 路径（原来多算了一层 `parent`）、子进程调用方式同步改
- **加 `__main__` 守卫**：Day 11 笔记的结论是"CLI 顶层不套守卫，因为没人 import CLI"——进包后**前提变了**（包成员天然可被 import）。把模块级代码收进 `main()`，加 `if __name__ == "__main__": main()`。前提变，结论跟着变
- 补关键注释（只补"为什么"级，不逐行翻译代码）：模块 docstring（一句话定位）、类 docstring（职责、`chat` 失败返回 `None` 的约定、Day 8 原子提交行为、重试策略）、`PRICES` 标注单位（元/百万 token）；CLI 的收尾出口注释已有，核对随迁完整
- **回归验证（今天的关键动作）**：重构完成后跑测试套件——零 API 8 用例必须全绿，真实 API 3 用例可选。重构的定义就是"不改行为"，证明不是"我觉得没改"，是测试说的。Day 11 readme 里写的"实验沉淀为回归资产"，今天第一次兑现价值

**坑位提示**：
- 进包后 `cli.py` 的 import 写法是 `from llm_client.client import LLMClient`（引用包名，不再是平级文件名）
- `python -m llm_client.cli` 要在**项目根目录**运行（cwd 决定包能否被找到）；README 的启动命令必须与此一致
- 测试的隔离机制（子进程 cwd = tmp_path）会与 `-m` 运行方式打架——包不在 tmp_path 下，找不到。最小改动解法：子进程 env 里加 `PYTHONPATH` 指向项目根。隔离不能丢（丢了就碰真实 history.json）
- `load_dotenv()` 从运行目录向上查找 `.env`：在项目根运行能向上找到，但求职仓库应自持 `.env`（从 `.env.example` 复制到项目根），README 写清放置位置

**检查点**：
- 新结构下程序能启动：普通聊天、三种退出、`/clear`、`/resume` 行为与 Day 11 一致
- 零 API 测试 8/8 全绿；import 项目包不触发任何 API 调用
- 每个文件职责单一，类文件有 docstring

**产出**：
- 文件：新项目目录下的 `client.py` / `cli.py` / `tests/test_cli.py`（自写，写完贴给 AI review）

### Step 4 · git init 与首次提交（类型：编码）

**前置依赖**：Step 2、3（README 与 `.gitignore` 都就绪，才有"规范的"首次提交可言）

**做什么**：
- 在项目根 `git init`
- 写 `.gitignore`（Step 1 第 3 问的清单落地）：`.env`、`.venv/`、`__pycache__/`、`.pytest_cache/`、`history.json`
- 写 `.env.example`：`API_KEY=` 与 `BASE_URL=` 两个占位（不带值）
- 提交前检查（顺序不能乱）：
  - `git add` 具体文件后先 `git status` 肉眼过一遍清单
  - `git ls-files` 确认：`.env` 不在、`.venv` 不在、没有 `__pycache__` / `history.json`
- 首次提交，message 规范（一行说清是什么），如：`feat: LLMClient 项目初始版本——多轮对话、历史持久化、错误重试、token 统计、命令行界面`
- 提交后 `git log` / `git show --stat` 复核入库内容

**坑位提示**：
- **顺序就是安全**：`.gitignore` 必须在 `add` 之前就位。一旦 `.env` 进了提交，事后 `git rm` 只是"下次不提交"，历史里那份还在——真正清除要改写历史（今天不学，记住后果即可）
- add 之前先看 `git status`，别无脑 `git add .`（把检查做在决定之前）
- 今天只建本地仓库，不 push（没有远程，也不必今天建）

**检查点**：
- `git ls-files` 输出只有应入库的文件
- `git log` 有一条规范的首次提交
- `git status` 干净

**产出**：
- 本地 Git 仓库 + 首次提交
