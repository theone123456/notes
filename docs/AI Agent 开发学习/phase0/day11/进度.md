## Step 拆解

### Step 1 · REPL 循环与命令分发（类型：概念）

**前置依赖**：Day 9 Step 5 自测 Q4（`chat` 失败返回 `None`，调用方怎么感知--当时留的悬念今天必须给出答案）；Day 10 的 `report()`（会话结束时打印，正好是今天退出流程的一部分）

**做什么**：
- 认识 REPL（Read-Eval-Print Loop）：读一行输入 -> 处理 -> 打印结果 -> 循环。Python 交互解释器、IPython、SQLite 的 `.help` 都是这个模式
- 对照一个转变：Day 2-10 的所有代码都是**脚本**（跑完即退、状态即消失）；今天的 CLI 是**持续运行的循环程序**--进程活着，`client.messages` 和 token 统计就一直活着
- 理解命令分发的本质：输入的第一道路由--先在本地判断是不是命令，**是命令就本地处理（不烧 token），不是才走 `client.chat()`**。判断顺序反了 = 每条命令都白付一次 API 调用
- 埋一个伏笔（记入笔记）：今天的结构 `while True: 读输入 -> 判断类型 -> 分发处理 -> 循环`，与阶段 2 的 **Agent 主循环**（`while` + `tool_calls` 分发）同构--输入来源从 `input()` 换成 LLM 的工具调用决策，分发分支从"命令 vs 聊天"换成"工具 A vs 工具 B"。今天写的是未来 Agent 的骨架雏形

**参考资料**：
- 无需外部资料；可让 AI 举 3 个"命令行程序用了 REPL 模式"的例子

**检查点**：
- 能画出/说出 CLI 主循环的四段结构（读、判、处理、循环）
- 能回答"为什么命令解析必须发生在调用 LLM 之前"
- 能说出脚本与持续运行循环程序在"状态生命周期"上的差别

**产出**：
- 笔记：记入 readme.md 的概念节

### Step 2 · CLI 设计四问（类型：思考）

**前置依赖**：Step 1；Day 8 design.txt 的结论（system prompt 定义人设与风格，load 时整体替换 messages）

**做什么**：
- 动手前先定方案（沿用 Day 8 的做法，结论写进 design.txt 或 readme.md），回答四个设计问题：
  1. **命令识别**：裸字符串匹配（输入等于 `exit` / `clear`）还是前缀约定（`/exit`）？各自代价：裸匹配实现最简，但用户永远没法聊"exit"这个词本身；前缀多敲一个字符，语义无歧义（SQLite `.quit`、聊天软件 `/` 命令都是这个思路）。二选一并写明理由
  2. **exit 语义**：退出前要做哪些收尾？`save` 要不要自动做（不自动做 = Ctrl+C 或忘敲命令就丢历史）？`report()` 放不放（Day 10 完成标志"会话结束打印总 token 和费用"的自然归宿）？收尾顺序怎么排？
  3. **clear 语义**：清到什么程度--连 system 消息一起清，还是保留 system、只重开对话（Day 8 design.txt Q1 的结论在这里兑现）？clear 之后 usage 统计清不清（想清楚再决定，依据见 Day 10 思考题结论：messages 是"接下来发什么"，usage 是"本进程花了多少"，两者生命周期不同）？
  4. **失败与中断**：`chat` 返回 `None`（Day 9 的重试后仍失败）时循环怎么办--打印提示后继续等下一条输入，还是退出？Ctrl+C / Ctrl+D（EOF）怎么处理才不会把裸 traceback 甩用户脸上？
- 写 2-3 句设计说明收口

**检查点**：
- 四问都有明确答案和理由
- 能说出"clear 不清 usage 统计"的依据（统计跟进程不跟会话，一个进程可能经历多个会话）
- 能回答"收尾动作为什么必须收敛成一条路径"（exit / Ctrl+C / Ctrl+D 三种退出都走它，漏一处就是一处丢历史）

**产出**：
- 笔记：设计结论记入 readme.md 的项目设计节（或 design.txt）

### Step 3 · 主循环骨架与命令分发（类型：编码）

**前置依赖**：Step 2 的设计结论

**做什么**：
- 开工准备：复制 `day10/llm_client_with_usage.py` 到 `day11/`；新建 `chat_cli.py`，顶部 `from llm_client_with_usage import LLMClient`（沿用 Day 10 实验脚本的库导入手法--`__main__` 守卫保证 import 那堆测试场景不会执行、不烧 token）。`chat_cli.py` 只放界面逻辑，为 Day 12 的文件拆分打样
- 写主循环骨架：`while True:` -> `input()` 读一行 -> 空输入直接 `continue` -> 命令分支（`/exit`、`/clear`，先占位即可）-> 其余作为聊天调 `client.chat()`
- 失败路径落地（Day 9 悬案的答案）：`reply is None` 时打印一行清晰提示（如"本轮调用失败，输入内容未记录，可重试或 /exit 退出"），**继续循环**--注意历史里不会有这条失败消息（Day 8 原子提交早已保证，今天只需确认行为，不用改类）
- 处理 `input()` 的两个中断：`KeyboardInterrupt`（Ctrl+C）和 `EOFError`（Ctrl+D）都捕获，走与 `/exit` 相同的收尾（本 Step 可先打印一句告别语占位，Step 4 补完整收尾）

**坑位提示**：
- `EOFError` 在交互式 CLI 里必须处理：终端里 Ctrl+D 意味着"输入流关闭"，不捕获就是丑陋崩溃
- 命令判断写循环内、`chat()` 之前--先调 LLM 再判断命令，等于给每条命令付一次 API 钱
- 别用 `eval` 或 `exec` 处理输入（任务只需要 if/elif 分发）

**检查点**：
- 程序能跑通：普通输入得到回复，命令能进对应分支，`/exit` 能退出（收尾可以是占位）
- 空输入、Ctrl+C、Ctrl+D 三种情况都不产生裸 traceback
- 库导入成功：`import` 时 day10 那套场景测试不会执行

**产出**：
- 文件：`chat_cli.py`（自写，写完贴给 AI review）

### Step 4 · exit / clear 完整语义 + 多轮使用体验（类型：编码 + 实验）

**前置依赖**：Step 3 的骨架

**做什么**：
- **编码部分**：
  - 实现收尾函数（单一出口）：`save()` -> `report()` -> 退出；`/exit`、Ctrl+C、Ctrl+D 三种退出方式都调用它。注意 save 的默认路径 `history.json` 是相对**运行目录**的（在 `day11/` 下运行就落在 `day11/history.json`）
  - 实现 `clear`：重置为 `[原始 system 消息]`（保留人设与风格约束），打印确认信息和当前消息数；usage 统计**不动**（Step 2 第 3 问的结论落地）
  - 可选进阶：加 `/resume` 命令调 Day 8 的 `load()`，恢复上次会话接着聊--让 Day 8 的成果在 CLI 里形成闭环（任务清单没要求，做不做自定，做了记入 readme）
- **实验部分**（任务清单原文："实际多轮使用，体验记忆效果"）：
  - 连聊 5 轮以上（自我介绍类问题沿用 Day 10 清单：报姓名年龄、说在学什么），中途问"我刚才说了什么"验证记忆
  - `/clear` 清空，再问刚才的自我介绍内容，验证失忆；接着聊新话题验证会话正常
  - `/exit` 退出后检查两件事：`history.json` 已更新（肉眼打开看），`report()` 已打印总 token 数和估算费用
  - 失败演练：临时用错 Key 启动一次（如 `API_KEY=wrong python chat_cli.py`），确认 CLI 不崩、提示清晰；顺手体验"每轮都失败"的循环是什么感受，思考要不要加"连续失败 N 次自动退出"--记录思考即可，不实现
  - 体验观察（记入 readme）：等待回复时命令行是**卡死状态**（同步阻塞）--阶段 1 的流式输出（stream）正是解药，记一笔伏笔

**检查点**：
- 三种退出方式（`/exit` / Ctrl+C / Ctrl+D）收尾一致：历史已存、报告已打印
- clear 后：旧话题失忆、新话题正常、统计未清零
- 有多轮使用体验的记录（记忆验证 + clear 失忆验证 + 失败演练）

**产出**：
- 文件：`chat_cli.py` 更新（自写，写完贴给 AI review）
- 实验数据：记入 readme.md 的实验记录节
