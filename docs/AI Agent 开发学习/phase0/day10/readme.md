# Day 10 学习笔记：Token 统计与成本估算

> 核心命题：把 usage 从"看得懂"变成"能算钱"--累计、估价、报告，三步闭环
> 产出脚本：`llm_client_with_usage.py`（Step 2-3 编码，复制自 day9）/ `cost_experiment.py`（Step 4 实验）

## 概念节：usage 字段全家福与计费公式（Step 1）

> 来源：Step 1 概念任务 · 地基：Day 4「按 token 计费」（输入/输出单价不同、prefill vs decode、reasoning_tokens 按输出价计费）· 目的：建立完整账单视图 + 成本估算的实现规格

### usage 三件套（复习）

```python
response.usage.prompt_tokens      # 输入：你发的 messages 编码后的 token 数
response.usage.completion_tokens  # 输出：模型生成的 token 数
response.usage.total_tokens       # = prompt + completion
```

Day 4 结论：输入输出**单价不同**，光看 `total_tokens` 算不了钱。

### 两个 details 子字段（今天的主角）

```python
response.usage.prompt_tokens_details.cached_tokens         # 输入里命中前缀缓存的部分
response.usage.completion_tokens_details.reasoning_tokens  # 输出里"思考"消耗的部分
```

**关键认知 1：details 是"拆细"，不是"另算"**

```text
prompt_tokens = 1000
├── 其中 cached_tokens = 600      ← 是 prompt_tokens 的子集，不额外加钱
└── 其余 400

completion_tokens = 2000
└── 其中 reasoning_tokens = 1500  ← 是 completion_tokens 的子集，不额外加钱
```

details 只是把账单拆细让人看清构成，`total_tokens` 早已包含全部。**算钱时 reasoning 不需要单独加项**。

**关键认知 2：每个子字段对应不同单价（glm-5.3，元/百万 token）**

| 计费项 | 对应字段 | 单价 |
|---|---|---|
| 标准输入 | prompt_tokens 中**未命中**缓存的部分 | 8.0 |
| 缓存命中输入 | cached_tokens | 2.0 |
| 输出（含思考） | completion_tokens **全部**，含 reasoning | 28.0 |

> 一句话：输入账单分两档（缓存价/标准价），输出账单一档但**思考不免费**--reasoning_tokens 按 28 元的输出价照收。

价格来源：Z.ai 官方定价（glm-5.3 与 5.2 同价）。方舟价格页目前只列到 glm-5.2（同为 8/28/2），glm-5.3 行未出现，**以方舟控制台计费明细为准**。

### 计费公式（Step 3 的实现规格）

**简化版**（不区分缓存，主用）：

```text
费用（元） = prompt_tokens × 输入单价 / 1e6 + completion_tokens × 输出单价 / 1e6
```

**精确版**（含缓存）：

```text
费用 = (prompt_tokens - cached_tokens) × 8 / 1e6
     + cached_tokens × 2 / 1e6
     + completion_tokens × 28 / 1e6
```

### glm-5.3 的坑：思考关不掉

- 思考模式**强制开启**，试图 disable 直接报错
- `reasoning_effort` 只有 low / high / max 三档，**默认 max**（最贵档）
- Z.ai 官方实测：同一分类任务，max 档中位输出 105 token，low 档只有 3 个

**Day 4 悬案闭环**：当时 deepseek-v4-flash 实验 completion 生成 100-600 token、存回 messages 的只有 5-78 token，推测"大头是看不见的推理"--对，就是 `reasoning_tokens`，**计费但不进 `message.content`**。Step 4 实验打印该字段实证。

### 单位坑（最常见的百万倍事故）

单价是"**元 / 百万 token**"，token 数要**除以 1,000,000** 再乘单价。忘了除，一轮闲聊算出几千块。校验直觉：一轮中文闲聊费用应在 **0.001 ~ 0.01 元**量级。

### 检查点自测记录（2026-08-26，三题通过）

> 原始作答：`self_test` · 3/3 全对，第 3 题分毫不差

1. **默写计费公式 + 输入输出为何分开乘单价** -- 通过
   - 默写的是精确版；价格差来自算力：输入 prefill 一次性并行计算，输出 decode 逐 token 各跑一次完整前向传播
2. **reasoning_tokens 藏哪、计入哪个口径、什么单价** -- 通过
   - `usage.completion_tokens_details.reasoning_tokens`，计入 completion_tokens，按输出单价--所以算钱不需要单独加项（第 3 题实际操作验证了这点）
3. **手算 1000 输入（600 缓存）+ 2000 输出（1500 思考）** -- 通过
   - 400×8/1e6 + 600×2/1e6 + 2000×28/1e6 = **0.0604 元** ✓

### review 补充的两个认知

**补充 1：缓存省了多少钱（实测数字）**

同样一组数据：不区分缓存的简化版 = 0.064 元，精确版 = 0.0604 元，差值 0.0036 = 600 × (8−2) / 1e6。输入费用从 0.008 降到 0.0044，**缓存把输入成本砍了 45%**--多轮对话里"固定 system + 稳定前缀"值钱的原因。

**补充 2："推理"一词的两个含义，别混**

| 词 | 指什么 | 出现场景 |
|---|---|---|
| 在线**推理** | inference，服务模式（相对于批量推理） | 方舟价格表 |
| **推理** token | reasoning，模型思考 | `reasoning_tokens` 字段 |

中文都叫"推理"，今天两个同时出现，读价格表时要分清。

## 本节记住五件事

1. **details 是拆细不是另算**：cached_tokens ⊂ prompt_tokens，reasoning_tokens ⊂ completion_tokens，算钱都不用单独加项
2. **输入两档、输出一档**：输入分缓存价/标准价；输出一档但思考照收 28 元/百万
3. **glm-5.3 思考关不掉且默认 max**：reasoning_effort 只有 low/high/max；Day 4"completion 远大于存回内容"的悬案就是它
4. **除以 1e6**：单位是元/百万 token；校验直觉--一轮中文闲聊 0.001~0.01 元
5. **缓存把输入砍 45%**：固定前缀（system + 早期历史）命中率是多轮对话省钱的核心旋钮

## 编码节：usage 累计器（Step 2）

> 来源：Step 2 编码任务 · 产出：`llm_client_with_usage.py`（复制自 day9，加累计器 + get_usage_summary）· review 一次通过

### 三个设计决策

**决策 1：累加位置 = 成功路径、return 之前、原子提交块内**

usage 只存在于 `response` 里，所以三行累加必须放在 `result = ...` 之后、`return result` 之前。两个典型错位：

- 放循环外 -> 语义变成"最后一次尝试"，但失败路径根本没走循环底部
- 放 except 里 -> `response` 不存在，NameError

**决策 2：失败调用天然不污染统计（不是选择，是事实）**

401 的请求被服务器**拒收**，没有生成任何 token，API 根本不返回 usage 对象（Day 9 实验 1 的报错里就没有）。超时重试后成功的调用，中间失败的那几次同样无账可记，只有最终成功的那次有 usage--统计天然干净。

**决策 3：从第一天就维护两个独立 token 计数器**

```python
self.total_prompt_tokens = 0
self.total_completion_tokens = 0
self.calls_succeeded = 0
```

不存 `total_tokens`--它是派生值（prompt + completion），在 `get_usage_summary()` 里现算，无冗余状态。只记总量的话，Step 3 按输入/输出分开乘单价时就得返工。

### 边界观察（review 指出，不是 bug）

SDK 类型标注里 `response.usage` 是 `Optional`。按 Day 9 Bug 4 原则（外部响应是系统边界），若 provider 不回 usage，当前代码会在 `self.messages +=` **之后**抛 AttributeError -> 落进兜底分支返回 None，但历史已被写入--半套副作用。实践里 glm-5.3 必回 usage，未改。**教训：原子提交块从 2 行涨到 5 行，副作用越长，原子性越要警惕。**

### 测试设计：快照差分法

单轮 usage = 调用前后两次 `get_usage_summary()` 快照之差（`after - before`）--与 Day 8 的 messages 快照是同一思想的两种应用：**快照 + 差分/提交，无副作用的读取方式**。断言"逐轮求和 == 累计值"完成对账。

### 验证（2026-08-26，四场景全绿）

| 场景 | 验证点 | 结果 |
|---|---|---|
| A 错 Key | 失败不污染统计 | 统计全 0，历史长度 1 ✅ |
| B 超时重试后放弃 | 重试失败也无账可记 | 统计全 0 ✅ |
| C 3 轮对账 | 快照差分求和 = 累计值 | 逐轮求和 == 累计 ✅ |
| D Day 8 回归 | 记忆 + save/load 无损 | 往返一致 True ✅ |

### 实验数据（场景 C，glm-5.3）

| 轮次 | prompt | completion | total |
|---|---|---|---|
| 1 | 43 | 76 | 119 |
| 2 | 65 | 85 | 150 |
| 3 | 110 | 77 | 187 |
| 累计 | 218 | 238 | 456 |

**观察 1：prompt 线性增长复现**。43 -> 65 -> 110，第 2 轮 +22、第 3 轮 +45--Day 4 的结论（每轮增量 = 上轮 user + assistant 存回内容）在本项目代码上验证，第 3 轮增量更大是因为历史里多了两轮问答。

**观察 2：completion 76~85，远小于 Day 4 deepseek 的 112~662**。glm-5.3 对简单问题思考很短。但存回的回复只有 20 多字（≈25 token），与 76~85 仍有差距--**思考占比多少，Step 4 打印 reasoning_tokens 见分晓**。

**观察 3：成本预告（Step 3 对账基准）**：

```text
218 × 8 / 1e6 + 238 × 28 / 1e6 ≈ 0.001744 + 0.006664 = 0.0084 元
```

落在"一轮闲聊 0.001~0.01 元"的校验直觉里。

**观察 4：load 恢复历史后，新实例统计全 0**。messages 决定"下轮发什么"（要持久化），usage 是"本进程花了多少"（生命周期不同）--Step 4 思考题正式讨论要不要持久化统计。

### 本节记住四件事

1. **累加跟历史同一条原子提交路径**：成功路径内、return 前；失败调用无 usage 可读，统计天然干净
2. **派生值不存状态**：total = prompt + completion 现算，状态最小化
3. **两个计数器从第一天分开**：成本按输入/输出分别乘单价，只记总量必然返工
4. **副作用越多，原子性越要警惕**：usage 为 None 的边界下，当前顺序会写历史后崩--边界字段先消费再提交

## 编码节：成本估算方法（Step 3）

> 来源：Step 3 编码任务 · 产出：`llm_client_with_usage.py` 加 PRICES 表 + estimate_cost + report（缓存精确版一步到位）· review 拦下 3 个问题

### review 拦下的三个问题（都是同一类病的不同症状）

**Bug 1：键名错位，一调就崩**。价格表定义 `input`/`output`/`cached`，取值却写 `["prompt"]`/`["completion"]` -> KeyError。说明方法写完**没运行过一次**。新增方法至少手动调一次。

**Bug 2：缓存 token 重复计费**。初版公式 `cached × 2 + prompt × 8 + completion × 28`，但 **cached ⊂ prompt**（Step 1 概念："details 是拆细不是另算"），缓存部分被收两次钱。正确：`(prompt − cached) × 8 + cached × 2 + completion × 28`。Step 1 检查点 1 概念题答对了，落到代码里却没生效--**概念理解的最后一公里，是能在代码里排除这类 bug**。

**Bug 3：接口改了，测试没跟上**。`get_usage_summary()` 新增 `cached` 键，场景 A 的 dict 相等断言还停留在四键版本，必挂。**接口（返回结构）变了，所有消费方都要跟着改**--这次是测试，下次就是实验脚本。

### 金标准值测试：用已手算过的数当用例（零 API 调用）

Bug 2 这类公式逻辑错，靠肉眼很难发现。解法：把 Step 1 手算过的数直接当断言值，不调 API、把计数器设成已知值：

```python
c2 = LLMClient(api_key="dummy")
c2.total_prompt_tokens, c2.total_cached_tokens, c2.total_completion_tokens = 1000, 600, 2000
assert math.isclose(c2.estimate_cost(), 0.0604)
```

cached > 0 的路径只有它能测到（实际调用里方舟未必回 cached_tokens）。**手算过一遍的数 = 免费的测试用例**。

### 设计决策：estimate_cost 里价格查不到，抛 KeyError 而不是兜底

`PRICES[self.default_model]` 直接索引，缺失自然 KeyError。三重理由：

1. **按数据归属选策略**：PRICES 表和 default_model 都是自己写的代码（内部不变量），fail loudly；API 响应里的 `prompt_tokens_details` 是外部数据，防御回落（`getattr`）。同一段代码里两种相反策略，不是不一致，是归属不同
2. **有没有合理默认值**：cached_tokens 缺失按 0 只损精度不损正确性；价格缺失任何默认值都产生**错误数字**--对成本统计功能来说，错误数字比崩溃更糟
3. **报错即文档**：`KeyError: 'glm-4.7'` 点名缺什么，traceback 指向哪里

验证判据一句话："模型能被调用，价格就该在表里；不在表 = 实现 bug"（fail fast）。**前瞻**：若将来 default_model 改为外部输入（构造参数/环境变量），验证点要前移到 `__init__`--非法值在进入系统的最早一刻拦截，越晚发现污染状态越多。

### 分层：estimate_cost 返回 float，report 做格式化

初版 `estimate_cost` 返回 `f"{cost:.6f}"` 字符串--实验脚本无法对费用做数学，且格式化混进接口。改为返回 float，`report()` 里格式化（`:.6f` + 换算成分）。**print 给人看，接口给代码看**（Day 9 教训第三次出现）。

### 验证（2026-08-26，五场景全绿）

| 场景 | 验证点 | 结果 |
|---|---|---|
| A 错 Key | 失败不污染统计（断言已补 cached 键） | 统计全 0 ✅ |
| B 超时重试后放弃 | 重试失败也无账可记 | 统计全 0 ✅ |
| C 3 轮对账 + 费用 | 快照差分求和 = 累计值 | 费用 0.009412 元（221×8+273×28 手算吻合）✅ |
| D 回归 + report() | 完成标志预演 | 报告正常输出 ✅ |
| E 金标准值 | 0.008408 / 0.0604 | 精确命中 ✅ |

### 实验数据（场景 C 第二次运行，glm-5.3）

| 轮次 | cached | prompt | completion | total |
|---|---|---|---|---|
| 1 | 0 | 43 | 102 | 145 |
| 2 | 0 | 65 | 96 | 161 |
| 3 | 0 | 113 | 75 | 188 |
| 累计 | 0 | 221 | 273 | 494 |

费用：221×8/1e6 + 273×28/1e6 = **0.009412 元**（约 0.94 分）。

**观察 1：cached 全程为 0，且无法区分"字段缺失"和"值为 0"**。两种可能：方舟没在 OpenAI 兼容字段里回 `prompt_tokens_details`，或确实没命中缓存。`getattr` 写法对两者都回落 0。结合方舟"透明前缀缓存，无需配置"的文档，若缓存实际生效，当前估算是**偏高的上界**--与 Step 4"与控制台对账"的可选任务呼应。

**观察 2：completion 波动**（102/96/75，上次 76/85/77）。同问题不同轮次输出长度自然波动，费用随之波动--**成本估算从来是估算，不是精确账单**。

### 本节记住五件事

1. **新代码至少跑一次**：Bug 1 那种一调就崩的错，运行一次就暴露，review 才发现是流程问题
2. **概念→代码的最后一公里**：cached ⊂ prompt 人人会背，公式里漏掉括号才是真实考验；金标准值测试是补刀手段
3. **接口变了，消费方全要跟着改**：dict 多一个键，相等断言就挂
4. **按数据归属选错误策略**：内部不变量 fail loudly（KeyError），外部数据防御回落（getattr）--同段代码两种策略是正确形态
5. **数值接口返回裸值**：格式化归 report/打印层；成本功能宁可崩在缺价格，不可静默给错数字

## 实验节：多轮成本观察（Step 4）

> 来源：Step 4 实验任务 · 产出：`cost_experiment.py`（库导入 LLMClient，非复制）· 已知前提裁剪：方舟链路 reasoning_tokens 恒 0 不做思考占比观察；方舟非纯单价计费口径，不做控制台对账

### 实验设计

- **实验 1**：5 轮固定对话（Day 4 同款问题清单，数据可横比）。每轮快照差分记录 token 与费用，费用拆成输入费/输出费（口径与 estimate_cost 一致，带拆分自检断言）
- **实验 2**：save -> 新进程 load -> 继续聊 1 轮，为思考题采集"重发重计费"数据
- 两个实现细节：**库导入**（`from llm_client_with_usage import LLMClient`，`__main__` 守卫保证 import 不烧 token，项目第一次"类被当库用"）；**费用差分**（estimate_cost 返回 float 兑现价值，单轮费用 = 前后两次调用之差，与 usage 差分同一手法）；**拆分自检**（split_cost 独立实现公式，与类内 estimate_cost 互为对照，两份实现算同一数）

### 实验数据（glm-5.3，2026-08-26）

| 轮次 | prompt | completion | 输入费(元) | 输出费(元) |
|---|---|---|---|---|
| 1 | 43 | 85 | 0.000344 | 0.002380 |
| 2 | 61 | 58 | 0.000488 | 0.001624 |
| 3 | 104 | 148 | 0.000832 | 0.004144 |
| 4 | 195 | 112 | 0.001560 | 0.003136 |
| 5 | 271 | 151 | 0.002168 | 0.004228 |
| 合计 | 674 | 554 | 0.005392 | 0.015512 |

总计：0.020904 元（约 2.09 分）。实验 2：恢复后第 1 轮 prompt 356 token（新会话第 1 轮仅 43）。

### 三个观察

**观察 1：输入占比逐轮爬升，但 5 轮内未反超**。输入费占比从第 1 轮 12.6% 爬到第 5 轮 33.9%。反超的数学条件：prompt > 3.5 × completion（输出/输入单价比 28/8）；第 5 轮仅 1.8x，外推约第 8-9 轮才交叉。结论：**短对话输出是大头（74.2%），长对话输入终将反超**--历史每轮重发、线性膨胀，这就是阶段 2 要学"历史截断/摘要压缩"的经济动因。

**观察 2：Day 4 悬案的算术闭环（字段为 0 也闭环了）**。用增量拆解：第 5 轮 prompt 271 − 第 1 轮 43 = 228 = user2~5（约 32）+ assistant1~4 存回（约 196）；但 5 轮 completion 计费合计 554，**554 − 196 ≈ 358 token（65%）计了费却不在 messages 里**。方舟虽然不报 reasoning_tokens（恒 0），算术证明了思考的存在：glm-5.3 思考关不掉，思考 token 计费但不进 message.content。**字段不报数 ≠ 没发生**。Day 4 悬案闭环：completion 远大于存回内容 = 看不见的思考在计费。

**观察 3：实验 2 量化了"重发重计费"**。恢复后第 1 轮 prompt 356 vs 新会话第 1 轮 43：**313 token 是旧历史重发**，仅此一项 313×8/1e6 = 0.0025 元，占本轮费用 45%--为一个已回答过的问题再付接近一半的钱，且随对话变长占比只会涨。

### 思考题：load 恢复历史后，旧会话的 token 统计该不该一起恢复？

> 原始作答：`self_test` · 结论正确（不恢复），review 修正一个论据 + 补齐"差分语义"解释

**结论：不恢复。当前进程级语义够用（Day 11 CLI 单进程一次会话）。**

正确论据（修正后）：

1. **生命周期不同**：messages 是"接下来要发什么"（要持久化），usage 是"本次进程花了多少"（进程级）
2. **report() 语义会自相矛盾**：恢复统计后，"成功调用 N 次"会包含本进程从未调过的旧调用，messages 长度与 calls 计数对不上
3. **成本收益**："会话累计"语义本身站得住（恢复的 313 token 是真实再付费，累加不是重复计算），放弃它的理由是**收益配不上复杂度**：save 文件格式要改（消息 + 统计一起存）、load 后要累加

**被推翻的论据**："两次请求 token 数不一样，所以没有参考价值"--不成立。其一方向反了：历史重发时 prompt_tokens 必然**更大**（新轮次历史更长），不是"不一样"；其二 token 数差异恰恰是参考价值所在（如实反映重发开销在增长）。同一会话各轮 token 本来就不同，没人因此说 usage 没有参考价值。

**"差分语义变复杂"的含义（review 展开）**：快照差分依赖计数器**单调递增、语义单一**。单轮差分在恢复后仍成立（before/after 都在同一进程内），真正出问题的是**跨进程对账**：A 进程"累计 0.0209 元"、B 进程 load 后"累计 0.0264 元"，两数都自称会话累计，但 B 看不到差额**何时**付的。要算清每轮的钱，必须把旧账新账**分账本**记，差分对分账本做、汇总再合并--一个计数器要同时回答"这轮花多少 / 会话累计花多少"两个问题，差分代码必须知道自己算的是哪个。**快照差分的前提：计数器语义唯一。**

### 本节记住四件事

1. **短对话输出贵、长对话输入贵**：输入占比逐轮爬升（12.6% -> 33.9%），反超条件 prompt > 3.5 × completion；历史压缩的经济动因
2. **字段不报数 ≠ 没发生**：reasoning_tokens 恒 0，但 554 计费 vs 196 存回的差值证明了思考在计费--算术闭环是字段缺失时的替代观测手段
3. **恢复历史 = 重发重计费**：313 token 旧历史占恢复后首轮费用 45%
4. **统计的生命周期跟进程，不跟会话**：messages 要持久化、usage 不用；跨进程恢复统计会让差分语义复杂化（一个计数器只能回答一个问题）
