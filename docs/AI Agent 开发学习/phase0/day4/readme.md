# Day 4 学习笔记：Token 与上下文窗口

> 核心命题：建立对 token 的直觉--它是计费、上下文管理、成本估算的最小单位
> 产出脚本：`token_experiment.py`、`multi_turn_tokens.py`、`token_estimate.py`

## Token：模型眼中的"一个字"

模型不认字符、不认单词，它只认 **token**。token 是一段固定长度的文本片段，被切成一个不可分割的整体。它的大小不固定，介于"字符"和"词"之间：

```text
英文 "hamburger"  -> "ham" + "burger"          = 2 个 token
英文 "apple"      -> "apple"（整词在词表里）    = 1 个 token
中文 "人工智能"    -> 可能切成 "人工" + "智能"   = 2 个 token
                  也可能切得更碎，取决于 tokenizer
```

**关键认知**：

1. **常见组合整个当一个 token，罕见组合被拆成碎片**。切得越碎，token 越多，越"贵"
2. **token 是模型处理和计费的最小颗粒度**。后面所有关于成本、上下文窗口的讨论，单位都是 token

## Tokenizer：切文本的"厨师刀"

tokenizer 是一个算法/工具，干一件事：**把一段文本切成 token 序列**。它的输入是一串人类文字，输出是一串 token（最终映射成整数 id 喂给模型）：

```text
"我喜欢学习AI"
   ↓ tokenizer 切分
["我", "喜欢", "学习", "A", "I"]   ← token 序列
   ↓ 查词表
[1234, 5678, 9012, 345, 678]        ← 整数 id 序列，模型真正处理的是这个
```

主流 tokenizer 采用 **BPE（Byte Pair Encoding，字节对编码）**：从单个字节/字符出发，反复合并语料里出现频率最高的相邻片段，直到词表达到设定大小。

> 一句话：tokenizer 是文本和模型之间的**翻译器**，它决定了"这段文字会被切成几份"。

### BPE 的切分逻辑

BPE 的核心思想：**反复合并语料里出现频率最高的相邻片段，直到词表达到目标大小。** 高频组合会被合并成整词 token，低频组合留在碎片状态。

**算法四步（循环执行）**：

```text
1. 把语料拆成最小单元（字符 / 字节），每个片段初始都是单个 token
2. 统计语料里所有"相邻 token 对"的出现次数
3. 取出现次数最多的那对，合并成一个新 token，加进词表
4. 回到第 2 步，直到词表达到设定大小
```

> 关键：合并顺序由频率决定。最高频的对先合并，常见词早早变成整词 token；罕见词轮不到合并，一直保持碎片。

**用一个小语料走一遍**（`</w>` 是词尾标记，BPE 用它区分词边界）：

```text
语料（按词拆开，标了出现次数）：
  t h e </w>    ×3    ← "the" 出现 3 次
  c a t </w>    ×2    ← "cat" 出现 2 次
  d o g </w>    ×1    ← "dog" 出现 1 次

初始词表（全是单字符）：{t, h, e, c, a, d, o, g, </w>}
```

```text
第 1 轮：统计相邻对，最高频是 (t,h)×3 -> 合并出新 token "th"
第 2 轮：(th,e)×3 最高频 -> 合并出 "the"
第 3 轮：(the,</w>)×3 -> 合并出 "the</w>"，"the" 现在是 1 个 token 了
第 4~6 轮：轮到 "cat" 的 (c,a)×2 -> (ca,t)×2 -> (cat,</w>)×2，"cat" 变整词
第 7~9 轮：(d,o)×1 -> (do,g)×1 -> (dog,</w>)×1，"dog" 也合完
```

**关键转折：换个语料看"碎片化"**。假设换个大语料，"dog" 一次都没出现过，`(d,o)`、`(o,g)` 这些对的频率被其他更高频的对压住，轮不到合并，"dog" 在词表里就始终是 `d` + `o` + `g` 三个碎片。推理时遇到新词 "fog"（训练时没见过）：

```text
"fog" 在词表里找不到整词 token
  ↓ 只能用已有碎片拼
"f" + "o" + "g"   = 3 个 token
```

> 这就是自测第 1 题的算法层面答案：罕见词没达到合并的频率门槛，留在碎片状态。

**中文为什么贵**。两大因素让中文吃亏：

| 因素 | 说明 |
|---|---|
| 词表以英文语料为主 | 英文里 `" the"`、`" hello"` 这类高频组合早被合并成整词 token（1 个）；中文常见词若不在高频统计里被合并，只能被拆成单字甚至子字碎片 |
| UTF-8 编码放大碎片 | GPT 系列用字节级 BPE，一个中文字在 UTF-8 里是 3 个字节。该字没被合并时光一个字就占 3 个 token，这就是"1 个中文字 ≈ 1~2 token"的来源 |

> 一句话：BPE 按频率合并，英文高频词赚到了整词 token，中文落在低频区被拆碎，所以同样信息量下中文 token 数更多、更贵。

## Vocab：固定的"字典"

vocab 是一张固定的对照表：每个 token 字符串 ↔ 一个整数 id。

```text
词表（vocab）节选：
  id=0     -> "!"
  id=1     -> "the"
  id=2     -> " hello"
  id=1234  -> "我"
  id=5678  -> "喜欢"
  ...
  id=50000 -> "</w>"   ← 特殊控制符
```

| 性质 | 说明 |
|---|---|
| 封闭的 | 词表大小固定（如 5 万、10 万），训练时就定死。模型这辈子只认识词表里这些 token |
| 切分受限 | tokenizer 只能用词表里已有的片段去拼文本。文本里没有"整个词"对应的 token，就只能被拆成更小的子词片段 |
| 各家不同 | GPT、Claude、DeepSeek、Qwen 的词表各做各的，所以同一个中文文本，不同模型切出来的 token 数不一样 |

## 三者的关系

```text
人类文本           tokenizer（切刀）         词表（vocab，查字典）        模型
"我喜欢AI"  ->  切成 ["我","喜欢","A","I"]  ->  查表得 [1234,5678,345,678]  ->  处理数字
```

- **token** 是产物（切出来的片段）
- **tokenizer** 是过程（切的动作）
- **vocab** 是依据（按什么切成这样）

## 按 token 计费

> usage 三件套（prompt_tokens / completion_tokens / total_tokens）已在 Day 2 笔记记录，本节聚焦计费机制

### 输入与输出单价不同

计费时光看 `total_tokens` 不够，算钱要按输入、输出分开乘单价：

| 计费项 | 字段 | 说明 |
|---|---|---|
| 输入 | `prompt_tokens` | 你发的 messages 编码后的 token 数 |
| 输出 | `completion_tokens` | 模型生成的回复 token 数 |
| 总量 | `total_tokens` | = prompt + completion，仅用于看总量 |

> 关键：输入和输出**单价不同，通常输出更贵**。报价表必须分输入/输出看，不能只看一个单价。

### 为什么输出更贵：prefill vs decode

价格差来自两种计算模式的算力差距。**输入不是只分个词就完事，也要跑完整模型**，但处理方式不同：

| | 输入（prefill 预填充） | 输出（decode 解码） |
|---|---|---|
| 处理方式 | 所有输入 token **一次性并行**计算 | **逐个生成**，每生成 1 个 token 跑一次完整前向传播 |
| N 个 token 的前向传播次数 | 约 **1 次** | 约 **N 次** |
| 算力消耗 | 低 | 高（约是输入的 N 倍） |

```text
输入 100 个 token  -> 1 次前向传播（并行搞定）
输出 100 个 token  -> 100 次前向传播（一个一个生成）
```

> 一句话：输出贵在"逐个生成"，每个 token 都要单独跑一遍模型；输入是并行处理，一次搞定。

**两个易混点**：

1. 工具调用是**外部操作**，不增加模型本身的算力成本，工具执行代价不计在 token 单价里
2. 推理模型多生成的 `reasoning_tokens` 也按**输出价**计费--那是"输出 token 多"，不是"单价高"

### 多轮对话的复利计费

因为模型**无状态**，每轮必须重发全部历史，而历史在之前轮次已经计过费--你不断为已付过费的内容重复买单。

```text
第1轮 prompt = system + user1                         = 100 token
第2轮 prompt = system + user1 + assistant1 + user2    = 160 token  ← user1 又付了一遍
第3轮 prompt = system + user1 + assistant1 + user2 + assistant2 + user3 = 220 token
```

> 关键：prompt_tokens 随轮数**线性增长**（每轮增量 ≈ 上一轮 user+assistant 的 token 数），不是指数级"利滚利"。但体感像复利，因为同样的历史被反复计费。

省钱靠的是**跨请求前缀缓存**：固定的 system + 早期历史是稳定前缀，命中缓存的部分按折扣价计费。

### 重复 token 不去重

token 计费看的是**序列长度**，不看去重后的种类数。同一个 token 出现 N 次，就计 N 次：

```text
"hello hello hello"
  ↓ tokenizer
["hello", " hello", " hello"]   = 3 个 token（3 个位置）
  ↓ 计费
prompt_tokens 计 3（不算 1）
```

每个 token 在序列里占一个**位置**，模型按位置逐个处理，账单按位置数算。重复的内容不会"合并算一次"。

| 机制 | 作用层面 | 效果 |
|---|---|---|
| 去重 | 不存在 | 单次请求内每个 token 位置都计费，无去重 |
| 前缀缓存（prefix caching） | 跨请求 | 若本次请求开头和上一次某请求开头一样，命中缓存的部分（`usage.prompt_tokens_details.cached_tokens`）按折扣价计费 |

> 一句话：同一段文本里重复的 token 每次都独立计费；想要折扣，靠的是让本次请求的开头尽量复用上一次的（前缀命中）。

## 上下文窗口（Context Window）

**上下文窗口 = 模型一次请求能处理的最大 token 数（输入 + 输出的总和）。** 它是模型的"工作台"：所有要处理的东西必须一次性全摊在台面上，超出了就装不下。

一次请求里，这些内容**全部算进**窗口预算：

```text
上下文窗口预算（比如 32K）
├── system prompt          ← 全局设定
├── 历史消息（user/assistant 交替）  ← 前几轮对话
├── 本轮 user 消息          ← 你这次问的
└── 模型本轮输出            ← 模型要生成的回复
```

> 注意第四项：**输出也算进窗口**。模型生成回复也要占额度，所以 `max_tokens` 有个隐含约束--不能大于"窗口剩余空间"，否则请求直接报错。

**预算例子**：窗口 32K，当前 messages 已占 30K token，那模型这次最多只能生成 2K token 的回复。设 `max_tokens=4000` 也只会报错或被截到 2K。

> 上下文窗口是**硬上限**（模型架构层面的物理限制，由位置编码、注意力机制等决定），不是建议值。跟计费无关--就算你愿意付钱，也塞不进超出窗口的内容。

### max_tokens：控制输出上限

`max_tokens` 是在 **API 请求参数**里设的，用来**限制模型这次最多能生成多少 token 的输出**：

```python
response = client.chat.completions.create(
    model=MODEL,
    messages=messages,
    max_tokens=1000,  # ← 限制输出不超过 1000 token
)
```

| 要点 | 说明 |
|---|---|
| 管的是输出 | 限制的是 `completion_tokens`（模型回复），不管输入 |
| 截断信号 | 回复撞到限制被截断时，`finish_reason` 返回 `"length"`（Day 2 学过） |
| 隐含约束 | 必须 ≤ 窗口剩余空间（窗口 - 输入已占），否则请求直接报错 |
| 不设会怎样 | 用模型/服务商的默认上限，通常远小于完整窗口（如默认 4K 而非 128K） |

### TPM / RPM：服务商的流量限速

TPM 和 RPM 是**服务商的流量限速**（rate limit），跟上下文窗口（模型能力上限）是两个不同维度：

| 限速 | 含义 | 触发后果 |
|---|---|---|
| **RPM**（Requests Per Minute） | 每分钟最多发多少次 API 请求 | 超了返回 429 rate limit 错误，要等 |
| **TPM**（Tokens Per Minute） | 每分钟最多处理多少 token（输入+输出） | 超了同样 429，要等 |

> 上下文窗口管"单次请求能塞多大"，TPM/RPM 管"一段时间内能用多频繁"。前者是模型能力，后者是服务商配额。

### 为什么最大输入 >> 最大输出 + 最大思考

观察到的现象：比如窗口 128K，但最大输出可能才 8K，最大思考可能 32K。原因就是上方的 prefill vs decode 算力差距--输出逐个生成成本高，服务商从三个角度压低上限：

1. **成本控制**：放任用户生成 128K 输出，单次请求算力成本会爆炸
2. **响应时间**：逐个生成意味着输出越长用户等越久，体验不可接受
3. **实际需求**：输入需要装下完整上下文，可以很长；回复通常几K token 已覆盖绝大多数场景

### 超出窗口的两种失败机制

超限发生在**两个不同阶段**，结果不同：

| 阶段 | 触发条件 | 结果 |
|---|---|---|
| 请求阶段（生成前） | 输入 > 窗口，或 `max_tokens` > 窗口剩余空间 | 请求直接**报错**，没生成 |
| 生成阶段（生成中） | 思考/回复达到窗口上限 | 立即**截断**，`finish_reason="length"` |

> 一句话：请求阶段超限是**报错**（拒收），生成阶段超限是**截断**（生成了但被砍断）。

少数实现会**静默截断**早期消息（不报错），这更危险--关键 system 或早期指令可能被悄悄丢掉（见下方位置策略）。

### Lost in the Middle 与位置策略

上下文窗口够大 ≠ 模型能用好全部内容。研究表明：模型对**开头和结尾**的信息利用率高，**中间部分容易被忽略**。

| 位置 | 放什么 | 原因 |
|---|---|---|
| 开头 | system prompt | 利用率高，稳 |
| 结尾 | 当前轮用户指令 | 利用率高，显眼 |
| 中间 | RAG 检索回来的文档 | 利用率低，所以要精选 + rerank，不能无脑堆 |

**工程对策**：超长对话有三大风险--报错/截断、丢关键 system、lost in the middle。对策是**自己先算 token、主动压缩历史**（截断/摘要/只检索相关历史），别把截断控制权交给服务商--你不知道它从哪开始砍，而 system 通常在最前面，静默截断最早被丢。

## 实验记录：英文/中文/代码 token 对比

> 产出脚本：`token_experiment.py` · 模型：glm-5.3
> 目的：验证同样信息量下，不同文本类型的 token 消耗差异

### 实验文本

三段文本主题都是"AI 预测"，信息量接近，字数自然不等：

```text
英文（148 字符）：
Artificial intelligence lets computers learn from data and make predictions. It powers search engines, recommendation systems, and chatbots like me.

中文（40 字符）：
人工智能让计算机从数据中学习并做出预测，它驱动着搜索引擎、推荐系统和聊天机器人。

代码（132 字符）：
def predict(model, data):
    result = model.run(data)
    if result.score > 0.8:
        return result.label
    return "unknown"
```

### 实验结果

每段单独作为单条 user 消息发送，记录 `usage.prompt_tokens`：

| 文本 | 字符数 | 输入 token | 字符/token | 换算 100 字的 token |
|---|---|---|---|---|
| English | 148 | 38 | 3.9 | ~26 |
| Chinese | 40 | 33 | 1.2 | ~83 |
| Code | 132 | 46 | 2.9 | ~34 |

### 结论

1. **中文 40 字消耗 33 token，英文 148 字才 38 token**。同样 100 字，中文 ≈ 83 token，英文 ≈ 26 token，中文每字符的 token 消耗约是英文的 **3 倍**
2. 中文约 **0.8 token/字**（1 ÷ 1.2），即"1 个中文字 ≈ 1 个 token"量级，与理论值"1-2 token/字"吻合
3. 原因：词表以英文语料为主，英文高频词整个进词表（1 token），中文被拆成单字甚至子字碎片；UTF-8 编码下 1 个中文字占 3 字节，放大碎片效应

### 逐轮拆解

每轮 prompt 增量 = 上一轮的 `assistant 存回 token` + 本轮 `user token`（user 约 8 token/条）：

| 轮次 | prompt 增量 | 拆解 | 存回的 assistant |
|---|---|---|---|
| 2 | 13 | assistant1 + user2(8) | ~5 |
| 3 | 48 | assistant2 + user3(9) | ~39 |
| 4 | 85 | assistant3 + user4(7) | ~78 |
| 5 | 85 | assistant4 + user5(8) | ~77 |

**异常发现**：completion_tokens 远大于存回的 assistant content token。例如第 1 轮生成 112 token，但存回 messages 的 assistant1 到第 2 轮只贡献约 5 token。推测 `deepseek-v4-flash` 生成了大量 `reasoning_tokens`（推理过程），这些计费但不存入 `message.content`。

### 结论

1. **prompt_tokens 随轮数线性增长**：95 -> 108 -> 156 -> 241 -> 326，每轮增量 = 上一轮 user + assistant 存回内容
2. **增量不恒定**（13 -> 48 -> 85 -> 85）是因为每轮 assistant 回复长短不同，但结构固定（每轮加一组 user+assistant）
3. **completion_tokens 与存回内容严重不符**：模型生成 100-600 token，存回只有 5-78 token，大头消耗在不可见的推理上
4. **输出增量正负交替是正常的**：每轮 completion 独立生成，与上轮无关，对比无意义，只看 prompt_tokens 增长趋势即可

## 实验记录：估算能力自测

> 产出脚本：`token_estimate.py` · 模型：glm-5.3
> 目的：建立"看一眼中文文本就能估出 token 数"的直觉

### 实验文本

三段不同长度的中文，先人工估再实际调用对比：

```text
短句（6 字）：今天天气真好
中等（32 字）：大语言模型通过预测下一个词来生成文本，核心是基于概率的序列建模。
长段（67 字）：Agent 是一个能感知环境、自主决策并调用工具完成目标的智能体系统，它的核心是 LLM 充当大脑，配合记忆、规划和工具使用形成闭环。
```

### 实验结果

| 文本 | 字符数 | 估算 | 实际 | 误差 |
|---|---|---|---|---|
| 短句 | 6 | 5 | 15 | -66.7% ❌ |
| 中等 | 32 | 25 | 30 | -16.7% ✅ |
| 长段 | 67 | 46 | 49 | -6.1% ✅ |

### 分析

用三个数据点反推，`prompt_tokens` 与字符数近似线性关系：

```text
prompt_tokens ≈ 0.56 × 字数 + 12
         纯文本率 ↑        ↑ 框架开销
```

误差主要来自**框架开销**（~12 token）：文本越短，开销占比越大，短句被拉偏到 -66.7%。中等和长段在 ±30% 以内，检查点达成。

### 结论

1. **检查点达成**：中等和长段在 ±30% 误差内 ✅，短句超限是框架开销占比过大导致
2. **可用的经验公式**：`prompt_tokens ≈ 字数 × 0.6 + 12`（glm-5.3）。日常快速估算中等以上文本：字数 ≈ token 数就够用
3. **框架开销意识**：估算时记得加 ~10-12 token 固定开销，文本越短影响越大

## 自测

1. **为什么罕见词会被切成碎片？**
   - 罕见词出现概率低，vocab 中没有对应的 token 与之匹配；tokenizer 只能用 vocab 里存在的 token 去拼文本，vocab 也不能临时扩容，就只能被切成碎片
   - 补充（BPE 视角）：BPE 训练时反复合并频率最高的相邻片段，罕见词出现次数少，没达到被合并成整词的频率门槛，所以训练结束后它仍以碎片形式留在词表里
2. **为什么 `" hello"` 和 `"hello"` 是不同 token？**
   - 空格被"吸收"进 token，而不是被拆开。`"hello"`（不含空格）和 `" hello"`（含前导空格）在词表里是**两个独立的条目**，各有各的 id，但都是单个 token
   - 原因：BPE 训练时，`" hello"`（前导空格+词）和 `"hello"`（词本身）在语料里出现语境、频率都不同，所以被训练成两个不同的 token
   - 工程意义：空格不是免费的。带空格的 JSON / 格式化文本比紧凑文本更吃 token，因为每个 `" word"` 都是独立 token
3. **同一段文本里重复的 token 怎么计费？**
   - **独立计费，按出现次数累加**。token 计费看的是序列长度（位置数），不看去重后的种类数。同一个 token 出现 N 次就计 N 次
   - 想要折扣不能靠"同请求内去重"（不存在这个机制），只能靠跨请求的**前缀缓存**：让本次请求开头复用上一次的，命中部分按折扣价
4. **为什么输出比输入单价贵？**
   - 两种计算模式的算力差距：输入是 prefill（所有 token **一次性并行**计算，N 个 token 约 1 次前向传播）；输出是 decode（**逐个生成**，每生成 1 个 token 跑一次完整前向传播，N 个 token 约 N 次前向传播）。同样 100 个 token，输出算力约是输入的 100 倍
   - 易混点：工具调用是外部操作，不增加模型算力成本；推理模型多生成的 reasoning_tokens 是"输出 token 多"，不是单价高的原因
5. **超长对话会怎样？（成本、窗口、注意力三个角度）**
   - **成本**：模型无状态，每轮重发全部历史，prompt_tokens 线性增长（实验验证：5 轮从 95 涨到 326），为已付过费的历史重复买单
   - **窗口**：请求阶段超限（输入 > 窗口或 max_tokens > 剩余空间）直接报错；生成阶段超限截断（`finish_reason="length"`）；服务商静默截断早期消息会丢掉 system prompt
   - **注意力**：lost in the middle--模型对上下文开头和结尾利用率高，中间容易被忽略，对话过长时中间信息可能丢失或回复失真

## 本节记住六件事

1. token 是模型处理和计费的最小单位：常见组合整个当一个 token，罕见组合被拆碎
2. tokenizer 按 vocab 切文本，vocab 是训练时定死的封闭词表--这就是中文更贵的根源
3. 空格是 token 身份的一部分：`" hello"` 和 `"hello"` 是两个不同的 token，格式化文本不免费
4. 重复 token 不去重：每个位置都独立计费，省钱靠跨请求的前缀缓存而非同请求内去重
5. 上下文窗口是硬上限：超限请求阶段报错、生成阶段截断；自己先算 token 主动压缩，别让服务商静默砍
6. lost in the middle：中间内容注意力低，重要信息放开头/结尾，RAG 文档放中间要精选 + rerank
