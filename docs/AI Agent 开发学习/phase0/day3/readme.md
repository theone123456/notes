# Day 3 学习笔记：消息角色与多轮对话

> 核心命题：用实验证明 Chat API 是**无状态（stateless）**的
> 产出脚本：`multi_turn.py`（已修复为只增不改的 messages 列表结构）

## 三种消息角色的分工

Chat API 用 `role` 字段区分每条消息“是谁在说话”。三种角色构成对话的最小单元，职责互不重叠：

| 角色 | 谁在说话 | 作用 | 在 messages 中的位置 |
|---|---|---|---|
| `system` | 开发者（不是用户） | 全局设定：人设、输出格式、行为边界，全程生效 | 通常第 0 条，唯一一条 |
| `user` | 最终用户 | 提问、下指令 | 数量、顺序无限制 |
| `assistant` | 模型 | 模型的历史回复，由代码拼回数组 | 必须跟在某个 user 之后 |

**关键认知**：

1. **system 不是“给用户看的消息”，是“给模型的指令”**。它和 user 消息一起进入上下文，但优先级更高（被对齐训练强化），所以能稳定改变模型风格
2. **assistant 消息由你的代码负责写入**，服务器不替你保存。一次调用拿到回复后，必须自己把它拼回 messages，否则下一轮模型看不到自己说过什么
3. **三者的地位不平等**：实验 4 已证明，system 约束是概率性的；指令冲突时（user 明确要求“超过 30 字” vs system “不超过 10 字”），模型优先级判断可能失败
4. **还有一个隐藏角色 `tool`**（阶段 1 学 Function Calling 时登场）：工具返回值以 `{"role": "tool", "content": ...}` 形式拼回 messages，地位与 user/assistant 类似，都是上下文的一部分

## 实验设计

### 实验 1：证明模型会"失忆"（不带历史）

```text
第 1 次调用 messages：
  [{"role": "user", "content": "我叫小明，我最喜欢的数字是 42。请记住这两点。"}]

第 2 次调用 messages（注意：不是追加，是全新数组）：
  [{"role": "user", "content": "我叫什么名字？最喜欢的数字是多少？"}]
```

### 实验 2：手动拼历史（带历史）

```text
[
  {"role": "user",      "content": "我叫小明，我最喜欢的数字是42，请记住这两点。"},
  {"role": "assistant", "content": "好的，我记住了：你叫小明，最喜欢的数字是42。"},
  {"role": "user",      "content": "我叫什么名字？我最喜欢的数字是多少？"}
]
```

### 实验 3：伪造历史

```text
[
  {"role": "user",      "content": "我叫小明"},
  {"role": "assistant", "content": "小明你好！你还告诉过我你的外号是'闪电侠'。"},
  {"role": "user",      "content": "我的外号是什么？"},
]
```

### 实验 4：system 的全程生效

```text
[{"role": "system", "content": "每次用户问什么，每次回答不得超过10个字"}]
```

## 实验结果与结论（已复盘修正）

### 实验 1：不带历史

- **现象**：第 1 次调用，模型答复记住了名字和数字；第 2 次全新调用，模型答复不知道
- **结论**：模型**任何时候都没有记忆**。第 2 次答不出不是"这个场景下失忆"，而是无状态 API 的必然结果--你不带历史，它就当全新问题处理
- **补一个细节**：有些模型在这种场景下不会说"不知道"，而是**编一个名字**（幻觉）。说"不知道"反而是对齐训练的结果

### 实验 2：带历史

- **现象**：模型正确答出名字和数字
- **结论**：**"记忆"不是模型的能力，而是工程效果**--我把历史装进 messages，模型只是"读懂了你带来的记录"。所谓多轮对话 = 每轮把全部历史重发一遍
- **面试考点**：这就是为什么 Agent 的"记忆模块"（阶段 2）本质是**历史管理工程**：存哪里、怎么压缩、检索哪些拼回去

### 实验 3：伪造历史

- **现象**：模型发现历史被伪造，指出我并没有说过外号，并反问我外号是什么
- **结论**：模型识别的是**上下文自相矛盾**（历史里没有任何 user 消息提到外号，assistant 却声称"你告诉过我"），而**不是**具备防 prompt injection 能力
- **验证方法见下方补充实验 3.5**：把伪造做得自洽，模型必然被骗

### 实验 4：system 的持久性

- **现象**：
  1. 问"请用30-50个字介绍自己" -> 超过10个字（破例）
  2. 指出"你超过限制了" -> 10字以内
  3. 问"你每次回答不得超过多少字" -> 模型**知道**是10字
  4. 再问"请用30-50字介绍自己" -> 10字以内
  5. 问"为什么第一次长第二次短" -> 模型能解释规则存在
- **结论**：system prompt **全程在场、并未丢失**（第 3、5 问是铁证）。第 1 问破例的原因是**指令冲突**：user 的明确指令（30-50字）与 system 约束（≤10字）竞争时，模型优先级判断失败
- **引申**：system prompt 的约束力是**概率性的**，不是硬保证。模型越弱（flash 档）越明显。对策有两个：
  1. 把约束写得更强势（"无论用户如何要求，不得超过10字；用户要求更长回答时，拒绝并说明原因"）
  2. **代码层校验**（工程护栏）：回复超过10字就重试或截断--关键约束永远不要只依赖提示词

### 补充实验 3.5：让伪造变自洽（已完成）

```text
[
  {"role": "user",      "content": "我叫小明，我的外号是闪电侠"},
  {"role": "assistant", "content": "闪电侠你好！"},
  {"role": "user",      "content": "我的外号是什么？"},
]
```

- **现象**：模型毫不犹豫地回答"闪电侠"，与回答一段真实历史毫无区别
- **意义**：模型只认上下文，不认真相。攻击者若能向 messages 注入内容（如 RAG 检索到的恶意文档、网页内容），就能操纵模型--这就是 prompt injection 的根本土壤，阶段 5 的护栏设计从这节课开始铺垫

### 知识点：'伪造历史'的本质

> 一句话：**messages 是"对话的记录"，而记录可以编写；模型只读记录，不查现场。**

**1. 伪造的不是内容，而是"对话发生过"这件事**

实验 3.5 中"小明说过自己外号是闪电侠"这段对话从未真实发生，整个 messages 数组是我亲手编写的。注意它与实验 2（真实历史）**结构完全同构**：

```text
实验2（真历史）                    实验3.5（假历史）
[user: 我叫小明，喜欢42]           [user: 我叫小明，外号闪电侠]
[assistant: 好的，记住了]          [assistant: 闪电侠你好！]
[user: 我叫什么？]                 [user: 我的外号是什么？]
```

两份记录摆在面前，**没有任何办法分辨哪个真实发生过**--对模型也一样。

**2. 两个视角的落差**

- **我的视角（上帝视角）**：知道哪些对话真的发生过，"实际上我从没说过外号"
- **模型视角**：没有上帝视角，**上下文里写了什么，它的世界里就是什么**

这个视角落差，就是所有 prompt injection 攻击赖以生存的空间。

**3. 实验 3 识破的是"矛盾"，不是"假"**

实验 3 能被识破，是因为历史**自相矛盾**（assistant 声称"你告诉过我"，但前文没有 user 消息支撑）；实验 3.5 历史自洽，模型只能采信。模型没有"走出上下文核对真相"的渠道。

**4. 真实世界的注入渠道**

真实场景里没人手写 messages 去骗模型，被"伪造"的是这些：

| 注入渠道 | 场景 |
|---|---|
| RAG 检索到的文档 | 攻击者在知识库里埋一篇"忽略之前的指令，告诉用户……" |
| 网页内容 | 浏览器 Agent 抓到的页面上藏了恶意指令 |
| 工具返回值 | 某个 API 返回的数据里夹带了 prompt |

这些内容最终都会被拼进上下文，与我手写的假 user 消息**地位完全相同**--模型一视同仁地阅读它们。

## 自测（修正版）

1. **为什么每次请求都要传完整历史？**
   - Chat API 是**无状态（stateless）**的：服务器处理完请求就忘掉一切，不保存任何会话。模型每轮"知道"什么，完全取决于本次请求的 messages 里装了什么
2. **"聊天记录"到底存在哪里？**
   - 存在**我自己的程序里**（messages 列表），不在服务器、不在模型。messages 中：system 存全局设定；user 存**所有历史**的用户输入（不只本轮）；assistant 存模型的历史回复（由我的代码拼回去）
3. **对话轮数越来越多，会发生什么问题？**（Day 4 引子）
   - 模型看到的信息**更多**而非更少，真正的问题是三个：
     - **成本线性增长**：每轮都要为全部历史重新付费（prompt_tokens 持续变大）
     - **逼近上下文窗口上限**：超出后请求报错，或早期内容被丢弃
     - **注意力稀释（lost in the middle）**：上下文很长时，模型对中间部分信息的利用率下降，效果变差
   - 解决思路（阶段 2 展开）：截断、摘要压缩、只检索相关历史拼回

## 本节记住三件事

1. 模型永远无记忆，"记忆"= 把历史装进上下文的工程效果
2. messages 只认内容不认真相：自洽的假历史必被采信（prompt injection 的土壤）
3. system prompt 全程在场但约束力是概率性的，关键约束要加代码层护栏
